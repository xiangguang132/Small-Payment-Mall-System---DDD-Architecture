# 待修复问题清单

本文档记录当前项目中生产需求单定时任务、生产接口以及相关库存链路还需要完善的点。

## 1. 生产任务名称现状

当前项目中没有名为 `ProductJob` 的定时任务类。

和商品生产最相关的定时任务是：

```text
s-pay-mall-ddd-trigger/src/main/java/cn.bugstack.trigger/job/ProductionOrderJob.java
```

它通过 `IProductionOrderService.executeCreatedOrders()` 执行待处理生产需求单。

## 2. 当前已完成的链路

目前生产需求单链路已经具备主流程：

1. 创建生产需求单：`POST /api/v1/production-order/create`
2. 查询生产需求单详情：`GET /api/v1/production-order/{id}`
3. 定时任务每分钟扫描待处理生产单
4. 执行生产单时创建原料分配单
5. 锁定原料库存
6. 原料自动出库
7. 成品入库到商品仓库库存
8. 生产单状态更新为完成

## 3. 高优先级待修复

### 3.1 生产执行缺少事务保护

位置：

```text
s-pay-mall-ddd-domain/src/main/java/cn/bugstack/domain/production/service/ProductionOrderService.java
```

`executeOrder(Long productionOrderId)` 当前没有 `@Transactional`。

该方法会连续操作：

1. 生产单状态
2. 原料分配单
3. 原料库存
4. 成品仓库库存
5. 生产单原料明细状态

如果中途失败，可能出现部分数据已经提交、部分数据没有提交的问题。

尤其是失败发生在“原料已出库，但成品还没有入库”之间时，当前 catch 逻辑会尝试 `release()`，但原料分配单已经不是锁定状态，释放可能失败，最终导致原料扣减但成品未增加。

建议：

1. 给 `executeOrder` 增加明确事务边界。
2. 重新设计失败补偿逻辑。
3. 区分锁库失败、出库失败、成品入库失败。
4. 已出库的原料不要再走简单释放逻辑。

### 3.2 失败后直接进入终态，缺少重试机制

当前生产单执行失败后直接更新为 `STATUS_FAILED = 3`。

问题：

1. 定时任务只扫描 `status = 0` 的生产单。
2. 失败单不会自动重试。
3. 没有保存失败原因。
4. 没有保存重试次数。
5. 没有下一次重试时间。

建议给 `production_order` 增加字段：

```sql
retry_count int default 0 comment '重试次数',
fail_reason varchar(512) default null comment '失败原因',
next_retry_time datetime default null comment '下次重试时间'
```

并新增状态：

```text
0 待处理
1 处理中
2 已完成
3 失败可重试
4 失败终态
5 已取消
```

### 3.3 定时任务缺少异常捕获

位置：

```text
s-pay-mall-ddd-trigger/src/main/java/cn.bugstack.trigger/job/ProductionOrderJob.java
```

当前 `exec()` 中只用 `finally` 释放 `running` 标记，没有 catch 日志。

建议：

```java
try {
    log.info("开始执行生产需求单任务");
    productionOrderService.executeCreatedOrders();
} catch (Exception e) {
    log.error("生产需求单任务执行异常", e);
} finally {
    running.set(false);
}
```

### 3.4 批量执行缺少单单隔离

位置：

```text
ProductionOrderService.executeCreatedOrders()
```

当前逻辑是查询 10 条待处理单并循环执行。

如果其中一条订单抛出未捕获异常，后面的订单可能不会继续执行。

建议：

1. 每个订单单独 try/catch。
2. 单个订单失败只影响自身。
3. 失败时记录订单 ID、订单号、失败原因。

## 4. 数据库结构待修复

### 4.1 状态字段类型和代码不一致

代码中生产单状态使用 `Integer`：

```java
private static final int STATUS_CREATED = 0;
private static final int STATUS_PROCESSING = 1;
private static final int STATUS_COMPLETED = 2;
private static final int STATUS_FAILED = 3;
```

但建表脚本中：

```sql
status VARCHAR(32) NOT NULL COMMENT '状态'
```

涉及文件：

```text
data/sql/production_order.sql
data/sql/production_order_material.sql
```

建议统一为：

```sql
status tinyint not null comment '状态'
```

或者代码全部改成枚举字符串。当前更建议使用 `tinyint`，和现有代码保持一致。

### 4.2 缺少唯一索引和查询索引

建议给生产单增加索引：

```sql
alter table production_order
    add unique key uk_order_no (order_no),
    add key idx_status_isdel_id (status, is_del, id),
    add key idx_product_warehouse_status_time (product_id, warehouse_id, status, create_time);
```

建议给生产单原料明细增加索引：

```sql
alter table production_order_material
    add key idx_production_order_id (production_order_id),
    add key idx_allocation_no (allocation_no);
```

### 4.3 防重复创建逻辑不可靠

当前通过 1 小时内相同 `productId + productQuantity + warehouseId + status` 判断重复。

问题：

1. 可能误伤正常重复生产。
2. 并发请求下仍可能插入重复数据。
3. 没有调用方业务请求号，无法真正幂等。

建议：

1. 请求中增加 `requestNo`。
2. `production_order` 增加 `request_no` 字段。
3. 建立唯一索引 `uk_request_no`。
4. 重复请求直接返回已有生产单 ID。

## 5. 接口待完善

当前 `ProductionOrderController` 只有：

```text
GET /api/v1/production-order/{id}
POST /api/v1/production-order/create
```

建议补充：

```text
GET  /api/v1/production-order/list?status=
POST /api/v1/production-order/{id}/execute
POST /api/v1/production-order/{id}/retry
POST /api/v1/production-order/{id}/cancel
```

用途：

1. `list`：方便前端或后台查看生产单。
2. `execute`：手动执行单个生产单，便于调试和运营处理。
3. `retry`：失败后人工重试。
4. `cancel`：待处理或失败单可以作废。

## 6. 业务建模待完善

### 6.1 缺少 BOM 或配方表

当前创建生产需求单时，调用方需要手动传入原料列表。

这意味着生产某个商品需要多少原料，是由前端或调用方决定的。

建议后续增加 BOM 表：

```text
product_bom
product_bom_item
```

创建生产单时只传：

```text
productId
productQuantity
warehouseId
```

系统根据 BOM 自动计算原料需求。

### 6.2 生产过程缺少审计记录

当前只更新最终状态，没有生产执行日志表。

建议增加：

```text
production_order_log
```

记录：

1. 生产单 ID
2. 操作类型
3. 原状态
4. 新状态
5. 操作结果
6. 失败原因
7. 创建时间

## 7. 原料分配任务现状

`MaterialStockAllocationJob.java` 当前整体被注释。

但当前生产单执行逻辑中已经同步调用：

```java
materialStockAllocationService.lock(allocationNo);
materialStockAllocationService.autoOutbound(allocationNo);
```

所以当前生产链路不依赖这个原料分配定时任务。

如果后续希望改成异步备料模式，需要重新设计：

1. 生产单创建原料分配单后进入“待备料”。
2. 原料分配任务负责锁库。
3. 锁库完成后生产任务再执行原料出库和成品入库。
4. 生产单状态需要能表达“待备料、备料中、备料完成、生产中”。

## 8. 测试待补充

当前项目没有发现 `*Test.java` 或 `*Tests.java` 测试文件。

建议至少补以下测试：

1. 创建生产单成功。
2. 商品不存在时创建失败。
3. 商品未上架时创建失败。
4. 仓库不存在或未启用时创建失败。
5. 原料不存在或禁用时创建失败。
6. 原料库存充足时执行生产成功。
7. 原料库存不足时生产失败。
8. 多个原料中后一个锁库失败时，前面已锁原料能释放。
9. 原料已出库后成品入库失败时，系统能正确补偿或标记异常。
10. 重复请求能返回同一生产单，而不是重复创建。
11. 定时任务执行时单个订单失败不影响其他订单。

## 9. 建议修复顺序

建议按以下顺序处理：

1. 修复 `executeOrder` 的事务边界和失败补偿。
2. 增加生产失败原因、重试次数、下次重试时间。
3. 增加定时任务异常捕获和单单隔离。
4. 修正 SQL 中 `status` 字段类型。
5. 增加唯一索引和查询索引。
6. 增加手动执行、列表、重试、取消接口。
7. 增加请求幂等字段 `requestNo`。
8. 补充服务层和库存链路测试。
9. 后续再引入 BOM/配方表。
