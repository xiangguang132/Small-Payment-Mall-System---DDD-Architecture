# 原料进货到销售链路完善清单

本文档记录当前项目从“原料进货”到“销售出库”的后续完善方向。

目标不是一次性把所有功能写完，而是按业务闭环逐步补齐：先让库存变化可信，再让生产和销售链路可追踪、可重试、可对账。

## 1. 总体业务链路

完整链路可以拆成以下阶段：

1. 原料采购或进货
2. 原料入库
3. 原料库存增加
4. 创建生产需求单
5. 原料分配、锁库、出库
6. 成品生产完成并入库
7. 创建销售订单
8. 销售订单支付或确认
9. 成品库存锁定、出库
10. 销售订单完成

当前项目已经具备一部分生产链路能力，下一步重点应放在库存流水、进货入库、销售出库和异常补偿上。

## 2. 当前已有基础

当前已有或正在完善的能力：

- 原料基础信息
- 原料库存
- 原料库存分配单
- 原料锁库、释放、出库
- 生产需求单
- 生产需求单定时执行
- 生产失败重试
- 成品仓库库存
- 商品、仓库等基础数据

这些能力已经能支撑演示型主流程，但还缺少完整的业务单据、库存流水和销售端闭环。

## 3. 第一阶段：原料进货入库

优先级：高。

这是整条供应链的起点。没有进货入库，原料库存只能靠手工初始化或直接修改库存，不利于追踪来源。

### 3.1 建议新增表

建议新增两类表：

```sql
purchase_order
purchase_order_item
```

如果暂时不想做完整采购，也可以先做更轻量的入库单：

```sql
material_inbound_order
material_inbound_order_item
```

建议字段：

- `inbound_no`：入库单号
- `request_no`：幂等请求号
- `supplier_id`：供应商ID，可后续补
- `warehouse_id`：入库仓库ID
- `material_id`：原料ID
- `quantity`：入库数量
- `status`：单据状态
- `remark`：备注
- `is_del`
- `create_time`
- `update_time`

### 3.2 建议新增接口

- `POST /api/v1/material-inbound/create`：创建原料入库单
- `POST /api/v1/material-inbound/confirm/{id}`：确认入库
- `GET /api/v1/material-inbound/{id}`：查询入库单详情
- `GET /api/v1/material-inbound/list`：分页查询入库单
- `PUT /api/v1/material-inbound/cancel/{id}`：取消未确认入库单

### 3.3 关键业务规则

- `requestNo` 必须唯一，防止重复入库。
- 入库数量必须大于 0。
- 原料必须存在且启用。
- 仓库必须存在且启用。
- 已确认入库的单据不能重复确认。
- 取消只允许发生在未确认状态。

### 3.4 入库后要做的事

确认入库时，不只是更新原料库存，还应该写库存流水：

1. 更新 `material_stock.available_qty`
2. 更新 `material_stock.total_qty`
3. 写入原料库存流水
4. 更新入库单状态为已入库

## 4. 第二阶段：库存流水

优先级：最高。

库存流水是整个供应链系统的账本。没有流水，就很难解释库存为什么变多、为什么变少，也很难排查线上数据错误。

### 4.1 原料库存流水

建议新增：

```sql
material_stock_flow
```

建议字段：

- `flow_no`：流水号
- `material_id`
- `warehouse_id`
- `stock_id`
- `biz_type`：业务类型
- `biz_no`：业务单号
- `change_qty`：变化数量
- `before_available_qty`
- `after_available_qty`
- `before_locked_qty`
- `after_locked_qty`
- `before_total_qty`
- `after_total_qty`
- `remark`
- `create_time`

### 4.2 原料库存流水类型

建议先定义这些类型：

- `INBOUND`：采购或进货入库
- `LOCK`：生产备料锁库
- `RELEASE`：锁定库存释放
- `OUTBOUND`：生产原料出库
- `ADJUST`：人工调整

### 4.3 成品库存流水

建议新增：

```sql
warehouse_stock_flow
```

流水类型：

- `PRODUCTION_INBOUND`：生产完成入库
- `SALE_LOCK`：销售锁定库存
- `SALE_RELEASE`：销售取消释放库存
- `SALE_OUTBOUND`：销售出库
- `ADJUST`：人工调整

## 5. 第三阶段：生产链路补强

优先级：高。

当前生产链路已经能跑主流程，后续重点是让状态流转更明确，让失败场景可恢复。

### 5.1 生产单状态建议

生产需求单状态建议保持清晰：

- `0`：待处理
- `1`：处理中
- `2`：已完成
- `3`：失败可重试
- `4`：最终失败
- `5`：已取消

### 5.2 需要补强的点

- 手动执行只允许待处理单据。
- 手动重试只允许失败可重试单据。
- 取消只允许待处理或失败可重试单据。
- 处理中单据不能直接取消。
- 执行生产单前需要防重复执行。
- 生产执行失败要记录失败阶段。
- 原料已经出库后再失败，不能简单释放库存，需要补偿方案。

### 5.3 推荐补偿方向

生产失败补偿不能只靠 `release`。

不同失败阶段要区别处理：

- 原料只锁定，未出库：可以释放锁定库存。
- 原料已出库，成品未入库：需要记录异常，进入人工介入。
- 成品已入库，状态更新失败：需要通过重试或对账修复状态。

## 6. 第四阶段：销售订单和销售出库

优先级：中高。

销售链路用于消耗成品库存，让项目形成“采购原料 -> 生产成品 -> 销售成品”的完整闭环。

### 6.1 建议新增表

```sql
sale_order
sale_order_item
```

建议字段：

- `order_no`：销售订单号
- `request_no`：幂等请求号
- `user_id`：用户ID
- `product_id`：商品ID
- `quantity`：购买数量
- `warehouse_id`：发货仓库ID
- `status`：订单状态
- `pay_status`：支付状态
- `remark`
- `is_del`
- `create_time`
- `update_time`

### 6.2 销售订单状态建议

- `0`：待确认
- `1`：待支付
- `2`：已支付
- `3`：已出库
- `4`：已完成
- `5`：已取消
- `6`：出库失败

如果暂时不接支付，也可以简化为：

- 待出库
- 已出库
- 已完成
- 已取消
- 出库失败

### 6.3 建议新增接口

- `POST /api/v1/sale-order/create`：创建销售订单
- `POST /api/v1/sale-order/confirm/{id}`：确认订单
- `POST /api/v1/sale-order/outbound/{id}`：销售出库
- `PUT /api/v1/sale-order/cancel/{id}`：取消订单
- `GET /api/v1/sale-order/{id}`：查询订单详情
- `GET /api/v1/sale-order/list`：分页查询订单

### 6.4 销售出库规则

- 商品必须存在且启用。
- 仓库必须存在且启用。
- 成品库存必须足够。
- 出库扣减必须使用条件更新，不能先查后改。
- 出库成功后写成品库存流水。
- 重复请求不能重复扣库存。

## 7. 第五阶段：任务和异常单

优先级：中。

当生产、入库、销售都跑起来后，需要补后台任务和异常处理能力。

### 7.1 建议新增任务

- 生产需求单自动执行任务
- 生产失败重试任务
- 原料锁定超时释放任务
- 销售出库失败重试任务
- 库存流水对账任务

### 7.2 异常单管理

建议增加异常查询能力：

- 生产失败单列表
- 原料库存分配失败单列表
- 销售出库失败单列表
- 需要人工介入单据列表

异常单里至少要能看到：

- 业务单号
- 失败阶段
- 失败原因
- 重试次数
- 下次重试时间
- 是否需要人工介入

## 8. 推荐开发顺序

建议按以下顺序推进：

1. 原料入库单
2. 原料库存流水
3. 生产单状态和手动操作补强
4. 成品库存流水
5. 销售订单
6. 销售出库
7. 销售出库失败重试
8. 异常单查询
9. 库存对账
10. BOM 物料清单

如果只看最近下一步，建议先做：

1. `material_inbound_order`
2. `material_inbound_order_item`
3. `material_stock_flow`
4. 原料入库确认接口

这四个做完以后，原料库存的来源就清楚了，后面的生产扣料也更容易解释。

## 9. 面试或项目说明表达

可以这样描述项目后续演进：

> 当前项目已经跑通商品、仓库、原料库存分配和生产需求单主流程。后续我会按供应链闭环继续补齐原料进货、库存流水、销售出库和异常补偿。重点不是简单增加接口，而是让每一次库存变化都有业务单据和流水支撑，保证库存数据可追踪、可对账、可恢复。

## 10. 当前最该避免的问题

- 不要直接手工修改库存数量作为业务入口。
- 不要只更新库存余额而不写流水。
- 不要让 Controller 直接编排库存变化。
- 不要让销售出库和生产出库复用含义不清的接口。
- 不要忽略 `requestNo` 幂等控制。
- 不要允许处理中单据随意取消。
- 不要把失败补偿简单理解成全部释放库存。

## 11. 小结

这条链路的核心不是表越多越好，而是每次库存变化都能回答三个问题：

1. 谁触发的？
2. 为什么变？
3. 变之前和变之后是多少？

只要能回答这三个问题，原料进货、生产扣料、成品入库和销售出库这条供应链就会越来越稳。
