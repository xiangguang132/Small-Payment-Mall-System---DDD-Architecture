# 微信扫码登录接口重写顺序说明

这份说明不是讲“业务含义”，而是讲“如果你要把微信扫码登录接口重新写一遍，文件应该按什么顺序创建，文件之间怎么调用”。

当前项目里这条链路已经拆成了 `trigger -> app -> domain -> infrastructure -> types` 这种 DDD 结构，所以正确写法不是先写 Controller，而是先把底层依赖准备好，再往上拼。

## 一、先看整体调用顺序

微信扫码登录实际分成 3 条主链路：

### 1. 获取二维码 ticket

前端请求后端：

`前端 -> LoginController.weixinQrCodeTicket() -> ILoginService.createQrCodeTicket() -> WeixinLoginService -> ILoginPort.createQrCodeTicket() -> LoginPort -> IWeixinApiService -> 微信公众平台`

返回结果：

`ticket`

### 2. 轮询登录状态

前端拿着 `ticket` 不断问后端：

`前端 -> LoginController.checkLogin(ticket) -> ILoginService.checkLogin(ticket) -> WeixinLoginService -> Guava Cache(openidToken)`

返回结果：

- 有值，说明扫码登录成功
- 没值，说明还没扫码或还没回调成功

## 二、如果从零重写，文件应该按什么顺序写

下面这个顺序是最稳的。核心原则只有一句话：

`先写被依赖的，再写依赖它的。`

### 第 1 步：先写 `types` 层

先把微信 XML 和统一返回体相关的基础能力准备好。

先写这些文件：

- [`MessageTextEntity.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-types/src/main/java/cn/bugstack/types/sdk/weixin/MessageTextEntity.java)
- [`XmlUtil.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-types/src/main/java/cn/bugstack/types/sdk/weixin/XmlUtil.java)
- `Response` 返回体
- `Constants.ResponseCode`
- `AppException`

为什么先写这一层：

- 微信回调进来的是 XML，不先有 `MessageTextEntity` 和 `XmlUtil`，你就没法解析请求体
- Controller 需要统一返回格式，不先有 `Response`，后面每个接口都会各写各的

### 第 2 步：再写 `api` / `domain` 的接口契约

先定义“要干什么”，不要先写“怎么干”。

先写这些接口：

- [`ILoginService.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-domain/src/main/java/cn/bugstack/domain/auth/service/ILoginService.java)
- [`ILoginPort.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-domain/src/main/java/cn/bugstack/domain/auth/adapter/port/ILoginPort.java)

这一步要做的事情：

- 定义 `createQrCodeTicket()`
- 定义 `checkLogin(ticket)`
- 定义 `saveLoginState(ticket, openid)`
- 定义 `createQrCodeTicket()` 的底层端口
- 定义 `sendLoginTempleteMessage(openid)` 的底层端口

为什么先写接口：

- 上层不用关心微信 API 怎么调
- 领域层不用关心 Retrofit、Redis、Guava Cache 怎么实现
- 后面实现时不会改来改去

### 第 3 步：写 `infrastructure` 层微信接口 DTO 和 Retrofit 接口

这一层负责把微信官方接口“翻译成 Java 可调用代码”。

先写这些文件：

- [`WeixinQrCodeRequestDTO.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-infrastructure/src/main/java/cn/bugstack/infrastructure/gateway/dto/WeixinQrCodeRequestDTO.java)
- [`WeixinQrCodeResponseDTO.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-infrastructure/src/main/java/cn/bugstack/infrastructure/gateway/dto/WeixinQrCodeResponseDTO.java)
- [`WeixinTemplateMessageDTO.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-infrastructure/src/main/java/cn/bugstack/infrastructure/gateway/dto/WeixinTemplateMessageDTO.java)
- [`WeixinTokenResponseDTO.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-infrastructure/src/main/java/cn/bugstack/infrastructure/gateway/dto/WeixinTokenResponseDTO.java)
- [`IWeixinApiService.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-infrastructure/src/main/java/cn/bugstack/infrastructure/gateway/IWeixinApiService.java)
- [`Retrofit2Config.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-app/src/main/java/cn/bugstack/config/Retrofit2Config.java)

这一步要注意：

- 先有 DTO，后有 Retrofit 接口
- 先有 Retrofit Bean，后有 `LoginPort`

因为 `LoginPort` 最终是靠 `IWeixinApiService` 发请求的。

### 第 4 步：写缓存配置

扫码登录的状态不是直接存数据库，而是先放缓存。

先写这些文件：

- [`GuavaConfig.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-app/src/main/java/cn/bugstack/config/GuavaConfig.java)

这里至少要准备两个缓存：

- `openidToken`：保存 `ticket -> openid`
- `weixinAccessToken`：保存 `appid -> access_token`

为什么这一层要放在 `app`：

- 它是运行时配置，不是领域规则
- 它只是给上层注入一个可用的缓存实例

### 第 5 步：写 `infrastructure` 的具体适配实现

这一层是真正调微信接口的地方。

先写这些文件：

- [`LoginPort.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-infrastructure/src/main/java/cn/bugstack/infrastructure/adapter/port/LoginPort.java)

它做两件事：

1. `createQrCodeTicket()`
   - 先取缓存里的 `access_token`
   - 没有就调微信 `getToken`
   - 再调微信创建二维码接口
   - 返回 `ticket`
2. `sendLoginTempleteMessage(openid)`
   - 先拿 `access_token`
   - 再发模板消息给微信

### 第 6 步：写 `domain` 服务实现

这一层负责把“登录业务动作”串起来。

先写这些文件：

- [`WeixinLoginService.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-domain/src/main/java/cn/bugstack/domain/auth/service/WeixinLoginService.java)

它只做业务编排，不直接碰微信 HTTP：

- `createQrCodeTicket()` 转调 `loginPort.createQrCodeTicket()`
- `checkLogin(ticket)` 查 `openidToken` 缓存
- `saveLoginState(ticket, openid)` 写缓存，再通知微信发模板消息

### 第 7 步：最后写 `trigger` 层控制器

触发层是最外层 HTTP 入口，最后写最稳。

先写这些文件：

- [`LoginController.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-trigger/src/main/java/cn.bugstack.trigger/http/LoginController.java)
- [`WeixinPortalController.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-trigger/src/main/java/cn.bugstack.trigger/http/WeixinPortalController.java)

这层只负责：

- 接收参数
- 调用应用/领域服务
- 返回 `Response`
- 处理微信回调 XML

不要把微信 API 调用写进 Controller。

## 三、推荐的实际编写顺序

如果你是照着重新写，建议直接按下面顺序建文件：

1. `types`
   - `MessageTextEntity`
   - `XmlUtil`
   - `Response`
   - `Constants`
   - `AppException`
2. `domain`
   - `ILoginService`
   - `ILoginPort`
   - `WeixinLoginService`
3. `infrastructure`
   - `WeixinTokenResponseDTO`
   - `WeixinQrCodeRequestDTO`
   - `WeixinQrCodeResponseDTO`
   - `WeixinTemplateMessageDTO`
   - `IWeixinApiService`
   - `LoginPort`
4. `app`
   - `Retrofit2Config`
   - `GuavaConfig`
   - 微信配置项
5. `trigger`
   - `LoginController`
   - `WeixinPortalController`

这个顺序的好处是：

- 每一步都有前一步能编译出来的依赖
- 不会出现“Controller 写好了，但 service 还没定义”的倒挂情况
- 你可以边写边跑，定位问题更快

## 四、如果你想按调用顺序理解，记住这个流程

### 获取 ticket

`前端请求 -> Controller -> Service -> Port -> 微信 API`

### 扫码成功

`微信回调 -> Controller -> 解析 XML -> Service -> Cache -> Port -> 微信模板消息`

### 前端轮询

`前端轮询 -> Controller -> Service -> Cache -> 返回登录结果`

---

## 五、你现在最容易写错的地方

1. 先写 Controller
   - 错
   - 因为 Controller 依赖最上层，但底层接口还没定义
2. 直接在 Controller 里调微信接口
   - 错
   - 微信调用应该放在 `infrastructure`
3. 不先写 XML 工具
   - 错
   - 微信回调是 XML，不先准备 `XmlUtil` 就没法解析
4. 不先写缓存配置
   - 错
   - 登录态没地方存，轮询接口就接不上

---

## 六、你可以把它理解成一句话

先写“数据载体和工具”，再写“接口契约”，然后写“基础设施实现”，接着写“领域编排”，最后写“HTTP 入口”。

如果你按这个顺序写，文件之间的依赖关系就会很清楚，不容易乱。
