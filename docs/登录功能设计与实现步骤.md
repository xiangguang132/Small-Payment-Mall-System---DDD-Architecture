## 1. 先搞清楚：这个登录功能到底在做什么

参考项目的登录链路不是“输入账号密码然后校验”，而是下面这条流程：

1. 前端先向后端申请一个微信扫码登录 `ticket`
2. 后端调用微信公众平台接口，拿到 `ticket`
3. 前端把 `ticket` 拼成二维码地址并展示给用户
4. 用户打开微信扫码
5. 微信公众号回调后端，通知“某个 `ticket` 已经对应某个 `openid` 登录成功”
6. 后端把 `ticket -> openid/token` 的登录状态写入缓存
7. 前端轮询检查这个 `ticket` 是否已经登录成功
8. 一旦成功，前端保存登录态并跳转首页

你可以把它理解成：

- `ticket` 是“这次登录请求的编号”
- `openid` 是“微信用户身份”
- `token` 是“前端后续访问系统时使用的登录凭证”

---

## 2. 最终目标是什么

实现后，你应该得到下面这几个能力：

1. 用户可以打开登录页看到二维码
2. 用户扫码后，后端能识别这次扫码属于哪个 `ticket`
3. 后端能把登录结果写到缓存或令牌系统中
4. 前端能轮询知道登录成功
5. 登录成功后前端能拿到 token 并跳转到首页

参考项目里当前做法是：

- `ticket -> openid` 存在 Guava Cache 里
- 二维码和微信回调通过公众号接口联动
- 模板消息用于提示用户扫码成功

## 4. 先做什么，后做什么

下面是推荐顺序。不要一上来就写 Controller，也不要先写前端页面。

### 第 1 步：先把登录链路画出来

先明确 5 个核心问题：

1. 登录入口是谁调用的
2. 登录状态存在哪里
3. 谁负责生成 `ticket`
4. 谁负责处理微信回调
5. 谁负责把登录状态告诉前端

这一步的目标不是写代码，而是先统一认知。

你要先定下来：

- `ticket` 从哪里来
- `openid` 从哪里来
- token 是什么格式
- 过期时间是多少
- 前端轮询频率是多少

推荐你先采用参考项目的方案：

- `ticket` 由后端向微信申请
- `openid` 由微信扫码回调携带
- token 可以先用 `openid` 或一个临时 token 表示，后面再升级为 JWT
- 轮询间隔 3 秒
- `ticket` 有效期 30 天

### 第 2 步：先定义接口，再写实现

先在 `api` 和 `domain` 里定义接口，不要急着连数据库、Redis、微信接口。

原因很简单：

- 接口先定义，后面实现不会乱
- 各模块职责更清楚
- 方便后续替换登录方式

### 第 3 步：再写应用层编排

应用层负责把登录流程串起来：

- 获取二维码 ticket
- 检查登录状态
- 保存登录态

应用层不应该关心微信接口怎么调，也不应该关心 Redis 怎么存。

### 第 4 步：再写基础设施实现

基础设施层去对接：

- 微信公众平台接口
- Redis / Cache
- 模板消息

这些都是技术细节，不能污染领域层。

### 第 5 步：最后写触发层和前端页面

触发层只负责：

- 接收 HTTP 请求
- 参数转换
- 调用应用/领域服务
- 返回结果

前端页面负责：

- 拉 ticket
- 展示二维码
- 轮询登录状态
- 保存 token

领域层只放业务规则和抽象，不放具体技术实现。

登录功能里，领域层应该表达的核心动作是：

## 5.6 微信公众号回调接口是整条链路的关键

参考项目通过公众号回调接收扫码事件：

- [参考项目微信公众号回调控制器](/D:/code/s-pay-mall-ddd/s-pay-mall-trigger/src/main/java/cn/bugstack/trigger/http/WeixinPortalController.java)

### 它做了什么

1. 验签
2. 接收微信消息
3. 判断是不是扫码事件
4. 读取 ticket
5. 调用 `loginService.saveLoginState(ticket, openid)`
6. 返回“登录成功”的公众号消息

### 你要注意的点

这个接口不是给浏览器调用的，是给微信服务器回调的。

所以你必须保证：

- 微信后台配置的回调地址正确
- 验签 token 正确
- 消息体 XML 解析正确
- 扫码事件里的 `ticket` 能拿到

## 6. 推荐你照着实现的具体顺序

下面给你一个非常实用的先后顺序。按这个做，最不容易乱。

### 第 1 轮：先把契约和骨架建出来

1. 确认 `api` 层登录接口需要哪些方法
2. 确认 `domain` 层需要哪些服务和端口
3. 在 `trigger` 层预留 `LoginController`
4. 在 `trigger` 层预留 `WeixinPortalController`

这一步不用管能不能跑通，先把类和方法签好。

### 第 2 轮：先让“ticket 获取”跑通

1. 在 `infrastructure` 层写微信 token 获取逻辑
2. 在 `infrastructure` 层写二维码 ticket 调用
3. 在 `domain` 层实现 `createQrCodeTicket()`
4. 在 `trigger` 层开放 `weixin_qrcode_ticket`
5. 用浏览器或 Postman 访问，确认能返回 ticket

这一轮成功后，至少说明你已经能拿到二维码地址了。

### 第 3 轮：再让“扫码回调”跑通

1. 配好微信公众号服务器回调地址
2. 微信扫码后能触发后端回调
3. 后端解析 XML，识别 `SCAN` 事件
4. 取到 `ticket` 和 `openid`
5. 调用 `saveLoginState(ticket, openid)`

这一轮成功后，说明后端已经知道“谁登录成功了”。

### 第 4 轮：再让“前端轮询”跑通

1. 前端拿到 ticket
2. 每 3 秒请求一次 `check_login`
3. 返回成功后停止轮询
4. 保存登录 token
5. 跳转首页

这一步是整个闭环的最后一环。

## 8. 数据流怎么走

你可以把整条链路记成下面这张图：


## 10. 推荐实现细节

### 10.1 token 不要直接长期用 openid

参考项目里注释提到，实际场景中可以把 `openid` 换成 JWT。

推荐做法是：

1. 登录成功后生成业务 token
2. 前端保存 token
3. 后续接口都带 token
4. 后端用 token 识别登录态

如果你只是学习流程，可以先用 `openid` 代替。

### 10.2 ticket 一定要有过期时间

不管你存缓存还是 Redis，`ticket` 都应该有超时时间。

推荐：

- 30 天

### 10.3 轮询不要太频繁

前端轮询建议：

- 2 到 3 秒一次

太快会给后端和微信接口造成额外压力。

### 10.4 回调接口要处理异常

回调接口是微信主动推送，请不要让异常直接炸掉。

建议：

- 尽量捕获异常
- 返回微信能接受的响应格式
- 记录日志

## 11. 验收标准

你可以用下面这组标准判断登录功能是否真正完成。

### 最基本验收

1. 打开登录页能看到二维码
2. 扫码后前端能在几秒内检测到登录成功
3. 登录成功后页面跳转
4. 后端日志能看到 ticket、openid、登录状态写入记录

### 更完整验收

1. 微信 access token 能缓存
2. ticket 过期后能重新生成
3. 回调接口验签能通过
4. 扫码事件能正确识别
5. 模板消息能发送成功

## 12. 常见坑

### 坑 1：先写前端，后端接口没定

这样很容易返工。

正确做法是先定接口，再写页面。

### 坑 2：把微信调用写进 Controller

不对。微信调用属于基础设施层。

### 坑 3：把缓存写进领域规则里

不对。领域层只表达业务规则，具体缓存实现放基础设施层。

### 坑 4：回调地址没配好

如果微信后台回调地址配置错了，扫码后后端根本收不到消息。

### 坑 5：ticket 和 openid 的关系没理清

你要始终记住：

- `ticket` 是登录会话编号
- `openid` 是微信身份
- `token` 是系统登录态

这三者不是一回事。
