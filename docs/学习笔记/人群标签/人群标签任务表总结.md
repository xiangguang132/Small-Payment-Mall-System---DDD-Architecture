# 人群标签任务 DAO 与 Mapper 一致性检查总结

更新时间：2026-08-13

## 1. 背景

本次对话围绕 `ICrowdTagsJobDao` 与 `crowd_tags_job_mapper.xml` 的一致性检查展开，目标是确认：

- DAO 中声明的方法在 mapper 中是否都有对应 SQL statement。
- mapper 的 namespace、参数、结果映射和字段是否完整。
- 当前删除任务等调用链是否能正常执行。

## 3. 检查时发现的问题

### 3.1 高：`deleteById` 缺少 mapper statement

`ICrowdTagsJobDao` 中声明了：

```java
void deleteById(Long id);
```

但 `crowd_tags_job_mapper.xml` 中缺少对应的 `deleteById` statement。

影响：

- 仓储层 `CrowdTagsJobRepository.deleteById` 会调用该 DAO 方法。
- 任务删除接口最终也会走到该调用链。
- 运行时会出现 `Invalid bound statement (not found)`，删除功能不可用。

### 3.2 低：`queryCrowdTagsJob` 查询语义不完整

DAO 方法返回单个 `CrowdTagsJob`，但原 SQL 只按 `tag_id` 和 `batch_id` 查询：

- 没有过滤 `is_del = 0`，可能查到已软删除任务。
- 没有限制单条结果，存在重复数据时可能触发 MyBatis 单对象映射异常。

该方法当前没有被仓储或服务层调用，属于潜在风险。

## 4. 修改内容

### 4.1 补齐 `deleteById` 软删 SQL

参考同类 `crowd_tags_mapper.xml` 的软删方式，在 `crowd_tags_job_mapper.xml` 中新增：

```xml
<update id="deleteById" parameterType="java.lang.Long">
    update crowd_tags_job
    set is_del = 1,
        update_time = now()
    where id = #{id}
      and is_del = 0
</update>
```

该实现不物理删除数据，而是将 `is_del` 置为 `1`，与任务列表、详情查询的软删除约定一致。

### 4.2 修正 `queryCrowdTagsJob` 查询条件

原 SQL：

```sql
where tag_id = #{tagId}
  and batch_id = #{batchId}
```

修改后：

```sql
where tag_id = #{tagId}
  and batch_id = #{batchId}
  and is_del = 0
limit 1
```

其余一致性确认：

- `queryPage`、`count` 的过滤条件一致。
- `queryById`、`updateStatus` 均带 `is_del = 0` 条件。
