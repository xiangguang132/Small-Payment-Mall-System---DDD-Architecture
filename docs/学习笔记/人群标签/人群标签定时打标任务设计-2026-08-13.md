# 人群标签定时打标任务设计

更新时间：2026-08-13

## 1. 背景

当前项目里已有三张相关表：

| 表 | 职责 |
| --- | --- |
| `crowd_tags` | 运营人工维护的人群标签元数据 |
| `crowd_tags_detail` | 系统写入的 tagId + userId 人群明细 |
| `crowd_tags_job` | 运营创建、系统执行的定时打标任务 |

`crowd_tags_job` 不是附带 `crowd_tags` 自动创建的，而是由运营单独创建一个任务，再按任务规则执行打标。

## 2. 核心结论

1. `crowd_tags_job` 存在必要。
2. 一个任务支持多次执行。
3. 运营负责创建任务、开启任务、关闭任务、删除过时任务。
4. 系统负责按任务字段执行，并写入执行结果和执行状态。
5. 不开放给 C 端用户，只开放给运营/后台使用。
6. 不做通用完整 CRUD，只做受控的创建、查询、开启、关闭、手动执行、软删除。
7. 不新增 `next_execute_time`，只保存 `last_execute_time`。

## 3. 数据表设计

### 3.1 `crowd_tags_job` 最终字段

| 字段 | 含义 | 写入方 |
| --- | --- | --- |
| `id` | 任务主键 | 系统 |
| `tag_id` | 要打标的人群标签 ID | 运营 |
| `batch_id` | 任务/批次标识 | 系统 |
| `tag_type` | 标签类型，例如 0 参与量、1 消费金额 | 运营 |
| `tag_rule` | 打标规则条件 | 运营 |
| `start_time` | 本次任务实际开始执行时间；运营触发执行后、系统开始执行前自动写入 | 系统 |
| `end_time` | 本次任务实际结束时间；任务自然结束或运营强制结束时自动写入 | 系统 |
| `status` | 任务状态 | 0/3 系统，1/2 运营 |
| `is_del` | 软删除标记；0 未删除，1 已删除 | 系统（运营通过删除接口触发） |
| `last_execute_time` | 系统最近一次实际执行时间 | 系统 |
| `create_time` | 创建时间 | 系统 |
| `update_time` | 最近修改时间 | 系统 |

### 3.2 字段约定

- `start_time` 和 `end_time` 不是运营填写的调度窗口，而是系统记录的实际执行起止时间。
- 运营点击执行后，系统在执行前先写入 `start_time`；任务自然结束或运营强制结束时，系统再写入 `end_time`。
- 如果后续还需要“允许执行的调度窗口”，应新增独立字段（例如 `schedule_start_time`、`schedule_end_time`），不要复用 `start_time`、`end_time`。
- `last_execute_time` 是系统真正执行任务后写入的时间，不能使用 `update_time` 代替。
- `update_time` 只表示记录最近被修改的时间，运营开启、关闭、系统执行后更新状态都会改变它。
- `is_del` 是独立软删除标记，不替代 `status`；`status` 只描述任务生命周期状态。
- `is_del = 1` 表示任务已经过时或不再需要，删除后保留历史明细和执行记录，但任务不再出现在运营列表，也不会被定时扫描或手动执行选中。
- 软删除时更新 `is_del = 1` 和 `update_time`，不物理删除数据。
- 不新增 `next_execute_time`。
- `stat_start_time`、`stat_end_time` 继续表示业务统计时间范围，与 `start_time`、`end_time` 的实际执行起止时间是两类字段，不要混用。
- 如果后续需要按业务数据时间范围统计，例如只统计某段时间的订单，需要在 `tag_rule` 中带上统计时间范围，或另行保留 `stat_start_time`、`stat_end_time` 字段。

## 4. 状态机设计

| status | 含义 | 写入方 |
| --- | --- | --- |
| 0 | 初始状态，任务刚创建 | 系统 |
| 1 | 计划/可执行，运营已开启任务 | 运营 |
| 2 | 关闭/停用，任务不再执行 | 运营 |
| 3 | 任务整体完成 | 系统 |

约定：

- `0` 由系统在创建任务时写入，即使创建动作由运营发起。
- `1` 由运营通过后台接口开启任务。
- `2` 由运营通过后台接口关闭任务。
- `3` 由系统在任务整体结束后写入。
- 运营写入 `1`、`2` 时通过接口操作，不直接修改数据库。
- `is_del` 独立于状态机；`status = 2` 是关闭/停用，不等于删除。
- 已删除任务通过 `is_del = 1` 表达，不再参与列表查询、定时扫描和手动执行。

## 5. 多次执行逻辑

一个 `crowd_tags_job` 行表示一个任务，而不是一次执行；同一任务可以被运营多次触发执行。

`start_time`、`end_time` 记录的是当前这次执行的实际起止时间。如果同一任务重复执行且需要保留每次执行历史，不能靠覆盖这两个字段保留；建议按执行生成 `batch_id`，或另建执行记录表。

建议流程：

```text
运营创建任务
  -> status = 0

运营开启任务
  -> status = 1

运营点击执行
  -> 系统先写入 start_time = 当前时间
  -> 执行任务

执行完成
  -> 写入 crowd_tags_detail
  -> 写入 Redis BitSet
  -> 更新 crowd_tags.statistics
  -> 系统写入 end_time = 当前时间
  -> 更新 last_execute_time
  -> 如果任务已整体结束，则 status = 3
  -> 如果任务仍可再次执行，则保持 status = 1

运营强制结束任务
  -> 系统写入 end_time = 当前时间
  -> status = 2

运营删除过时任务
  -> is_del = 1
  -> 保留历史明细和执行记录
  -> 不再出现在运营列表
  -> 不再被定时扫描或手动执行选中
```

如果“重置”表示重新执行，建议单独提供“重置”动作，不要让 `status = 2` 同时承担关闭和重置两种含义。

## 6. 系统执行逻辑

系统执行时，`TagService.execTagBatchJob(tagId, batchId)` 应按以下顺序处理：

1. 查询 `crowd_tags_job`，条件包含 `is_del = 0`。
2. 校验任务存在、未删除且允许执行。
3. 系统写入 `start_time`，表示本次执行已开始。
4. 根据 `tag_type` 和 `tag_rule` 解析打标规则。
5. 根据规则查询需要打标的用户列表。
6. 将用户写入 `crowd_tags_detail`。
7. 将用户写入 Redis BitSet，保证运行期命中。
8. 更新 `crowd_tags.statistics`。
9. 系统写入 `end_time`，表示本次执行已结束；任务整体结束时 `status = 3`，任务仍可再次执行时保持 `status = 1`，运营强制结束时 `status = 2`。
10. 更新 `last_execute_time`。

## 7. `tag_rule` 的作用

`tag_rule` 是决定给哪些用户打标的条件。

`tag_type` 决定按什么指标计算，`tag_rule` 决定具体阈值或条件。

示例：

| tag_type | tag_rule | 含义 |
| --- | --- | --- |
| 0 | 10 | 参与量大于等于 10 |
| 1 | 1000 | 消费金额大于等于 1000 |
| 1 | {"operator":"GE","value":1000} | 结构化表达消费金额大于等于 1000 |

如果当前还没有真实用户采集逻辑，`tag_rule` 可以先保存，但后续系统自动打标时必须读取它来生成查询条件。

## 8. 新增接口设计

接口只开放给运营/后台，不开放给 C 端用户。

文档中的 `/admin` 表示“后台管理接口”的逻辑归属，不是强制要求；实际接口路径以项目现有风格为准，本项目统一使用 `/api/v1/crowd-tags/jobs`。

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/api/v1/crowd-tags-jobs` | POST | 创建任务，系统写入 `status=0` |
| `/api/v1/crowd-tags-obs/{id}/plan` | POST | 开启任务，运营写入 `status=1` |
| `/api/v1/crowd-tags-jobs/{id}/disable` | POST | 关闭任务，运营写入 `status=2` |
| `/api/v1/crowd-tags-jobs/{id}/execute` | POST | 手动立即执行任务；系统先写入 `start_time`，结束时写入 `end_time` |
| `/api/v1/crowd-tags-jobs/{id}` | DELETE | 软删除任务，系统写入 `is_del=1` |
| `/api/v1/crowd-tags-jobs` | GET | 分页查询任务列表 |
| `/api/v1/crowd-tags-jobs/{id}` | GET | 查询任务详情 |

不提供通用 `update` 接口，也不提供物理删除接口；`DELETE` 只做软删除。
列表和详情默认只返回 `is_del = 0` 的任务，已删除任务不展示。
软删除接口不要求先关闭任务，删除后立即停止参与执行；手动执行已删除任务按不存在/不可执行处理。

创建任务时，运营传入：

- `tagId`
- `tagType`
- `tagRule`

系统自动写入：

- `batchId`
- `status = 0`
- `createTime`
- `updateTime`
- `lastExecuteTime = null`
- `isDel = 0`

`startTime`、`endTime` 不在创建任务时由运营传入，而是在系统执行开始时和结束时分别自动写入。

## 10. 待确认点

1. `batch_id` 是任务级标识，还是每次执行单独生成。
2. 是否需要“重置”动作，以及重置后如何生成新的执行批次。
3. `tag_rule` 使用简单字符串，还是结构化 JSON。
4. 如果打标需要按业务数据时间统计，是否需要恢复 `stat_start_time`、`stat_end_time`。
5. 软删除后是否需要恢复能力；如果不需要，删除即为终态。
6. `start_time`、`end_time` 记录单次执行起止；如果同一任务需要保留多次执行历史，应确认 `batch_id` 是否按执行生成，或另建执行记录表。

## 11. 先确认口径（建议默认值）

为了不把代码反复重写，建议先按下面 3 个默认值落地第一版：

1. `batch_id` 建议在创建任务时由系统生成并固定，格式例如 `yyyyMMddHHmmss + 6 位随机`，长度控制在 32 以内。手动执行和定时执行都复用同一个 `batch_id`，只更新 `start_time`、`end_time`、`last_execute_time`。该方案不保留“每次执行”的历史；如果后续必须保留历史，应新增执行记录表，不要把 `crowd_tags_job` 既当任务又当执行历史。
2. `tag_rule` 第一版先保存为字符串，但代码里做一个规则解析器，兼容 `10`、`1000`、`{"operator":"GE","value":1000}` 三种写法，后续再统一成结构化 JSON 也不会改接口。
3. 第一版先做“后台手动执行 + 定时扫描 `status = 1` 的任务”，不一开始做异步任务和分布式锁。任务量变大后再给执行入口加 Redis 分布式锁，或增加执行记录表。

如果确认需要每次执行都生成新 `batch_id`，则不要覆盖任务行里的旧批次，建议改成：

```text
crowd_tags_job           只保存任务配置
crowd_tags_job_execution 保存每次执行，包括 batch_id、start_time、end_time、status
crowd_tags_detail        增加 batch_id，记录本次明细来源
```

下面按“第一版不新增执行记录表”继续写。

## 13. 参考代码

### 13.1 SQL

首次执行：

```sql
ALTER TABLE `crowd_tags_job`
    ADD COLUMN `start_time` DATETIME NULL COMMENT '本次任务实际开始执行时间' AFTER `tag_rule`,
    ADD COLUMN `end_time` DATETIME NULL COMMENT '本次任务实际结束时间' AFTER `start_time`,
    ADD COLUMN `last_execute_time` DATETIME NULL COMMENT '最近一次实际执行时间' AFTER `status`,
    ADD COLUMN `is_del` TINYINT NOT NULL DEFAULT 0 COMMENT '软删除；0未删除、1已删除' AFTER `last_execute_time`;

ALTER TABLE `crowd_tags_job`
    MODIFY COLUMN `status` TINYINT NOT NULL DEFAULT 0 COMMENT '状态；0初始、1计划/可执行、2关闭/停用、3任务整体完成',
    MODIFY COLUMN `batch_id` VARCHAR(32) NOT NULL COMMENT '任务/批次标识';
```

如果列已经存在，跳过对应的 `ADD COLUMN`，不要重复执行。

### 13.5 统计量更新

不要把参考项目里的“传入本次 userIdList.size()”直接搬过来，重复执行会失真。建议改为按明细表去重统计：

```xml

<update id="updateCrowdTagsStatistics" parameterType="cn.bugstack.infrastructure.dao.po.crowdtags.CrowdTags">
    update crowd_tags c
    set c.statistics = (
    select count(1)
    from (
    select 1
    from crowd_tags_detail d
    where d.tag_id = #{tagId}
    ) t
    ),
    c.update_time = now()
    where c.tag_id = #{tagId}
    and c.is_del = 0
</update>
```

### 13.7 `CrowdTagsExecuteService` 执行顺序

```java
@Service
public class TagService implements ITagService {

    @Resource
    private ITagRepository tagRepository;

    @Resource
    private ICrowdUserCollectService crowdUserCollectService;

    @Override
    public void execTagBatchJob(String tagId, String batchId) {
        CrowdTagsJobEntity job = tagRepository.queryCrowdTagsJobEntity(tagId, batchId);
        if (job == null
                || !Integer.valueOf(1).equals(job.getStatus())
                || Integer.valueOf(1).equals(job.getIsDel())) {
            throw new AppException(ResponseCode.NOT_FOUND, "人群标签任务不存在或不可执行");
        }

        LocalDateTime now = LocalDateTime.now();
        tagRepository.updateStartTime(job.getId(), now);

        List<String> userIdList = crowdUserCollectService.collect(job);
        for (String userId : userIdList) {
            tagRepository.addCrowdTagsByUserId(tagId, userId);
        }

        tagRepository.updateCrowdTagsStatistics(tagId);
        tagRepository.updateFinishTime(job.getId(), LocalDateTime.now(), finishStatus(job));
    }

    private Integer finishStatus(CrowdTagsJobEntity job) {
        // 第一版：统计时间已结束就按“任务整体完成”处理；否则保持可再次执行。
        if (job.getStatEndTime() != null && LocalDateTime.now().isAfter(job.getStatEndTime())) {
            return 3;
        }
        return 1;
    }
}
```

### 13.8 任务管理服务

```java
@Service
public class CrowdTagsJobService implements ICrowdTagsJobService {

    @Resource
    private ICrowdTagsJobRepository jobRepository;

    @Resource
    private ITagService tagService;

    @Override
    public Long create(CrowdTagsJobEntity job) {
        validate(job);
        LocalDateTime now = LocalDateTime.now();
        job.setBatchId(buildBatchId());
        job.setStatus(0);
        job.setIsDel(0);
        job.setCreateTime(now);
        job.setUpdateTime(now);
        return jobRepository.save(job);
    }

    @Override
    public void execute(Long id) {
        CrowdTagsJobEntity job = jobRepository.queryById(id);
        if (job == null || Integer.valueOf(1).equals(job.getIsDel())) {
            throw new AppException(ResponseCode.NOT_FOUND, "人群标签任务不存在");
        }
        if (!Integer.valueOf(1).equals(job.getStatus())) {
            throw new AppException(ResponseCode.CONFLICT, "人群标签任务未开启");
        }
        tagService.execTagBatchJob(job.getTagId(), job.getBatchId());
    }

    @Override
    public void executeReadyJobs() {
        for (CrowdTagsJobEntity job : jobRepository.queryExecutableJobs()) {
            try {
                execute(job.getId());
            } catch (Exception e) {
                log.error("人群标签任务自动执行失败 jobId:{}", job.getId(), e);
            }
        }
    }
}
```

### 13.10 定时任务

参考现有 `ProductionOrderJob` 的开关和防重入写法：

```java
@Slf4j
@Component
public class CrowdTagJob {

    @Value("${crowd.tag.job.enabled:false}")
    private boolean enabled;

    private final AtomicBoolean running = new AtomicBoolean(false);

    @Resource
    private ICrowdTagsJobService crowdTagsJobService;

    @Scheduled(cron = "${crowd.tag.job.cron:0 0/10 * * * ?}")
    public void exec() {
        if (!enabled) {
            log.info("人群标签任务未开启，本次跳过");
            return;
        }
        if (!running.compareAndSet(false, true)) {
            log.info("人群标签任务正在执行，本次跳过");
            return;
        }
        try {
            crowdTagsJobService.executeReadyJobs();
        } catch (Exception e) {
            log.error("人群标签任务执行异常", e);
        } finally {
            running.set(false);
        }
    }
}
```

## 14. 验证建议

1. DAO 测试：创建任务后能按 id 查询；`status=1`、`is_del=0` 能被 `queryExecutableJobs` 扫到；删除后详情查询不到。
2. 服务测试：未开启任务不能执行；已删除任务不能执行；执行后 `start_time`、`end_time`、`last_execute_time` 被更新。
3. 集成测试：执行一次任务后，`crowd_tags_detail` 有明细，Redis `RBitSet` 命中用户为 true、未命中用户为 false。
4. 定时任务：配置 `crowd.tag.job.enabled=true` 后，确认只扫描可执行任务，不扫描关闭/删除任务。

## 15. 实现时不要踩的坑

- 不要用 `update_time` 代替 `last_execute_time`，前者表示记录最近被修改，后者表示系统真正执行任务。
- 不要用 `status = 2` 表达删除，删除统一用 `is_del = 1`。
- 不要在 `crowd_tags_job` 上做通用 update，创建后只允许系统更新执行时间和状态，运营通过接口执行 plan/disable/delete。
- 不要沿用参考项目 `statistics = #{statistics}` 的覆盖式更新，改成按明细表统计。
- 真实采集逻辑不要直接写死在 `CrowdTagsExecuteService`，先通过 `ICrowdUserCollectService` 隔离。
- 如果以后要做执行历史，优先新增执行记录表，而不是在任务行里反复覆盖 `batch_id`。
