# 微信扫码登录接口面试说明

这份说明以当前项目里的微信扫码登录链路为例，回答面试时最常见的几个问题：

- 这个接口从哪一层开始写
- 每一层分别负责什么
- 整个接口怎么串起来
- 面试官可能会追问什么

当前项目里，这条链路主要涉及 3 个 HTTP 接口：

- [`LoginController.weixinQrCodeTicket()`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-trigger/src/main/java/cn.bugstack.trigger/http/LoginController.java)
- [`LoginController.checkLogin()`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-trigger/src/main/java/cn.bugstack.trigger/http/LoginController.java)
- [`WeixinPortalController.post()`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-trigger/src/main/java/cn.bugstack.trigger/http/WeixinPortalController.java)

---

## 一、先说结论

这个接口不是“一个 Controller 里写完”，而是按 DDD 分层实现：

1. `trigger` 层接收 HTTP 请求
2. `domain` 层负责登录业务编排
3. `infrastructure` 层负责对接微信接口、缓存、模板消息
4. `app` 层负责 Spring Bean 配置
5. `api` 和 `types` 层提供统一返回体、公共常量和通用模型

一句话概括：

> `trigger` 只负责收发请求，`domain` 负责业务规则，`infrastructure` 负责技术实现。

---

## 二、推荐的写代码顺序

如果要从零重写，建议按下面顺序来：

1. 先写 `types`
2. 再写 `domain` 的接口和业务服务
3. 再写 `infrastructure` 的微信 API 和适配器
4. 再写 `app` 的缓存和 Retrofit 配置
5. 最后写 `trigger` 的 Controller

原因很简单：

- 先定义抽象，再写实现，结构最稳
- 上层不会反向依赖下层的技术细节
- 后面改微信接口或缓存方案时，影响面更小

## 四、接口是怎么实现的

### 1. 申请二维码 ticket

接口：

- `GET /api/v1/login/weixin_qrcode_ticket`

调用链：

`LoginController.weixinQrCodeTicket() -> ILoginService.createQrCodeTicket() -> WeixinLoginService -> ILoginPort.createQrCodeTicket() -> LoginPort -> IWeixinApiService -> 微信公众平台`

实现过程：

1. Controller 收到请求
2. 调用 `loginService.createQrCodeTicket()`
3. `WeixinLoginService` 把请求转给 `LoginPort`
4. `LoginPort` 先从缓存取 `access_token`
5. 缓存没有就调微信 `getToken`
6. 再调微信创建二维码接口，拿到 `ticket`
7. Controller 包装成统一响应返回给前端

关键代码：

- [`LoginController.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-trigger/src/main/java/cn.bugstack.trigger/http/LoginController.java)
- [`WeixinLoginService.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-domain/src/main/java/cn/bugstack/domain/auth/service/WeixinLoginService.java)
- [`LoginPort.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-infrastructure/src/main/java/cn/bugstack/infrastructure/adapter/port/LoginPort.java)

### 2. 轮询检查登录状态

接口：

- `GET /api/v1/login/check_login?ticket=xxx`

调用链：

`LoginController.checkLogin() -> ILoginService.checkLogin(ticket) -> WeixinLoginService -> Guava Cache`

实现过程：

1. 前端带着 `ticket` 轮询
2. Controller 调用 `checkLogin(ticket)`
3. `WeixinLoginService` 直接去缓存查这个 `ticket`
4. 如果缓存里有值，说明扫码登录成功
5. 如果没有值，说明还没扫码或微信回调还没完成

这里 `ticket -> openid` 的映射存放在 `openidToken` 缓存里。

缓存配置：

- [`GuavaConfig.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-app/src/main/java/cn/bugstack/config/GuavaConfig.java)

### 3. 微信扫码回调

接口：

- `POST /api/v1/weixin/portal/receive`

调用链：

`微信服务器 -> WeixinPortalController.post() -> XmlUtil -> ILoginService.saveLoginState(ticket, openid) -> Guava Cache -> ILoginPort.sendLoginTempleteMessage(openid)`

实现过程：

1. 微信用户扫码后，微信服务器主动回调后端
2. Controller 解析 XML 请求体
3. 判断消息类型是不是 `event`，事件是不是 `SCAN`
4. 如果是扫码事件，就取出 `ticket` 和 `openid`
5. 调用 `saveLoginState(ticket, openid)`
6. 把 `ticket -> openid` 写入缓存
7. 再发送模板消息通知用户登录成功

关键代码：

- [`WeixinPortalController.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-trigger/src/main/java/cn.bugstack.trigger/http/WeixinPortalController.java)
- [`WeixinLoginService.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-domain/src/main/java/cn/bugstack/domain/auth/service/WeixinLoginService.java)
- [`LoginPort.java`](/D:/code/s-pay-mall-ddd-cc/s-pay-mall-ddd-infrastructure/src/main/java/cn/bugstack/infrastructure/adapter/port/LoginPort.java)

## 五、为什么这样分层

面试时可以这样回答：

1. 先把 HTTP 入口和业务分开，避免 Controller 变胖
2. 把登录状态管理放在 domain，方便以后替换缓存或 token 方案
3. 把微信 API 调用放在 infrastructure，避免领域层依赖外部 SDK
4. 统一返回体和响应码，前后端交互更清晰

这个设计的核心价值是：

- 可维护
- 可替换
- 可测试
- 依赖方向清楚

## 七、面试官可能会问的问题

### 1. 为什么不用数据库存登录状态？

可以回答：

- 这是短生命周期的临时状态，缓存更合适
- 轮询频繁，缓存读写更快
- 数据库适合持久化，不适合做高频状态流转

### 2. 为什么 `ticket -> openid` 放在缓存里？

可以回答：

- `ticket` 是这次扫码登录的临时标识
- `openid` 是微信用户身份
- 二者是一次性关联关系，缓存足够

### 3. 为什么 `createQrCodeTicket()` 要先拿 `access_token`？

可以回答：

- 微信创建二维码 ticket 需要先有 `access_token`
- `access_token` 是调用微信 API 的通行证
- 所以先查缓存，缓存没有就去微信拉取

### 4. 为什么把微信调用放在 `infrastructure`？

可以回答：

- 微信接口属于外部依赖
- 领域层不应该依赖具体 SDK 或 HTTP 客户端
- 放到 `infrastructure` 更符合依赖倒置原则

### 5. `trigger` 层为什么不直接写业务？

可以回答：

- `trigger` 应该保持轻薄
- 它只负责协议适配，不负责业务规则
- 这样接口切换、前端改动时影响更小

### 6. 扫码回调为什么要解析 XML？

可以回答：

- 微信公众号回调默认就是 XML 格式
- 后端需要先把 XML 转成对象，才能读取 `ticket`、`openid`、`event`

### 7. 如果缓存宕机了怎么办？

可以回答：

- 当前实现会影响登录状态查询
- 生产上可以把缓存换成 Redis
- 业务不变，只改基础设施层实现

### 8. 这个设计如何扩展成 JWT 登录？

可以回答：

- 现在缓存里存的是临时登录态
- 后续在 `saveLoginState()` 成功后，可以签发 JWT
- 前端拿到 JWT 后用于后续接口访问

## 八、面试时可以直接背的简短版本

你可以这样说：

> 这个微信扫码登录接口是按 DDD 分层实现的。`trigger` 层负责接收 HTTP 请求和返回结果，`domain` 层负责登录业务编排和登录态管理，`infrastructure` 层负责调用微信公众平台接口和发送模板消息，`app` 层负责缓存和 Retrofit 的 Bean 配置。整体流程是先向微信申请二维码 `ticket`，用户扫码后微信回调后端写入 `ticket -> openid`，前端再轮询 `check_login` 判断是否登录成功。

## 十、总结

这套接口的实现思路可以概括为：

1. `trigger` 层收请求
2. `domain` 层编排业务
3. `infrastructure` 层调微信
4. `app` 层提供缓存和客户端
5. `types` / `api` 层提供公共模型

如果你面试时要讲，只要抓住这条主线就够了：

`申请 ticket -> 扫码回调 -> 写缓存 -> 轮询确认登录`
