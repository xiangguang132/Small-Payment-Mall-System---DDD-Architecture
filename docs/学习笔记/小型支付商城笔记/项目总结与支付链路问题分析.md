# 项目总结与支付链路问题分析

本文档是对 `s-pay-mall-ddd-cc` 整个项目的总结，重点分成三部分：

1. 这个项目实现了什么
2. 具体是怎么实现的，按关键文件逐行说明
3. 过去出现过什么问题，以及这次支付异常的判断

---

## 1. 项目实现了什么

这个项目是一个按 DDD 分层拆出来的商城支付与登录系统，核心能力有两条：

- 微信扫码登录
- 支付宝沙箱支付下单、回调更新、超时补偿

从业务上看，它完成了这些事情：

- 用户可以通过微信扫码登录
- 用户可以发起商品下单，系统生成支付宝支付单
- 用户支付成功后，支付宝异步通知系统
- 系统收到回调后把本地订单改成已支付
- 如果回调丢失，系统会通过定时任务补偿查询
- 如果订单长时间未支付，系统会自动关单

从架构上看，它按典型 DDD 分成了 6 个模块：

- `s-pay-mall-ddd-api`：对外接口和请求响应 DTO
- `s-pay-mall-ddd-app`：Spring Boot 启动、配置、MyBatis 映射、应用资源
- `s-pay-mall-ddd-domain`：领域层，放订单和登录的业务编排
- `s-pay-mall-ddd-infrastructure`：基础设施层，放 DAO、仓储适配、第三方接口调用
- `s-pay-mall-ddd-trigger`：触发层，放 HTTP Controller、定时任务、事件监听
- `s-pay-mall-ddd-types`：公共类型、常量、工具、事件基类

---

## 2. 整体调用链

支付链路可以先记成一句话：

`Controller -> Service -> Repository -> Dao -> Mapper XML -> Database`

更完整一点的支付流程是：

1. 前端调用创建支付单接口
2. `AliPayController` 进入 `OrderService.createOrder(...)`
3. 先查本地有没有未支付订单
4. 没有就查商品信息并创建本地订单
5. 调支付宝接口生成支付表单
6. 把支付表单回写到本地订单
7. 支付宝支付成功后回调 `pay_notify`
8. 回调验签通过后更新本地订单状态
9. 定时任务补偿未收到回调的订单
10. 定时任务关闭超时未支付订单

### 3.1 `../../../s-pay-mall-ddd-app/src/main/java/cn/bugstack/Application.java`

```java
@SpringBootApplication
@Configuration
@EnableScheduling
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

逐行说明：

- `@SpringBootApplication`：Spring Boot 主启动注解，开启组件扫描、自动配置等能力。
- `@Configuration`：把这个类标记成配置类。
- `@EnableScheduling`：开启定时任务能力。没有它，`@Scheduled` 不会生效。
- `public class Application`：Spring Boot 启动类。
- `main(...)`：Java 程序入口。
- `SpringApplication.run(...)`：启动整个 Spring 容器和 Web 服务。

这里最关键的是 `@EnableScheduling`，因为订单补偿和超时关单都依赖它。


- 这是支付宝异步通知入口

```java

if (request.getParameter("trade_status").equals("TRADE_SUCCESS")) {
```

- 先打印回调状态。
- 只有 `TRADE_SUCCESS` 才继续处理。

```java
Map<String, String> params = new HashMap<>();
Map<String, String[]> requestParams = request.getParameterMap();
for (String key : requestParams.keySet()) {
    params.put(key, request.getParameter(key));
}
```

```java
boolean checkSignature = AlipaySignature.rsa256CheckContent(content, sign, alipayPublicKey, "UTF-8");
```

- `out_trade_no` 是商户订单号，也就是本地订单号。
- `sign` 是支付宝签名。
- `getSignCheckContentV1(...)` 会把参数拼成待验签串。
- `rsa256CheckContent(...)` 用支付宝公钥验证签名是否正确。

```java

    log.info("支付回调，交易名称: {}", params.get("subject"));
    log.info("支付回调，交易状态: {}", params.get("trade_status"));
    log.info("支付回调，支付宝交易凭证号: {}", params.get("trade_no"));
    log.info("支付回调，商户订单号: {}", params.get("out_trade_no"));
    log.info("支付回调，交易金额: {}", params.get("total_amount"));
    log.info("支付回调，买家在支付宝唯一id: {}", params.get("buyer_id"));
    log.info("支付回调，买家付款时间: {}", params.get("gmt_payment"));
    log.info("支付回调，买家付款金额: {}", params.get("buyer_pay_amount"));
    log.info("支付回调，支付回调，更新订单 {}", out_trade_no);
    orderService.changeOrderPaySuccess(out_trade_no);
}
```

- 验签通过后，打印回调关键信息。
- 调用 `orderService.changeOrderPaySuccess(out_trade_no)` 把本地订单改成已支付。

```java
return "success";
```

- 无论是否更新成功，接口最后都返回 `success`。
- 这是支付宝异步通知的惯例，避免支付宝重复重试。

## 4. 微信扫码登录实现了什么

这个项目不只有支付，还实现了微信扫码登录。

对应入口：

- `../../../s-pay-mall-ddd-trigger/src/main/java/cn.bugstack.trigger/http/LoginController.java`
- `../../../s-pay-mall-ddd-trigger/src/main/java/cn.bugstack.trigger/http/WeixinPortalController.java`
- `../../../s-pay-mall-ddd-domain/src/main/java/cn/bugstack/domain/auth/service/WeixinLoginService.java`
- `../../../s-pay-mall-ddd-infrastructure/src/main/java/cn/bugstack/infrastructure/adapter/port/LoginPort.java`

登录流程大致是：

1. 前端请求二维码 ticket
2. 后端调用微信接口生成 ticket
3. 前端拿 ticket 拼出二维码
4. 用户扫码后，微信回调后端
5. 后端把 `ticket -> openid/token` 写入缓存
6. 前端轮询 `check_login`
7. 有值则登录成功

这个链路和支付链路一样，都是典型的“入口层接请求，领域层做流程，基础设施层接外部系统”的 DDD 写法。

## 6. 这次“支付宝已支付，本地没变”的当前判断

基于现有代码和日志，当前更像是下面这个问题：

- 定时任务已经启动了
- 补偿任务也在跑
- 但日志里没有看到一次成功的 `支付回调，消息接收 TRADE_SUCCESS`

这说明问题优先怀疑：

1. 支付宝异步通知没有打到本机
2. `notify_url` 对应的外网穿透地址不可达
3. 穿透域名和本地服务之间的转发出了问题
4. 支付宝后台配置的通知地址不是当前实际可访问地址

也就是说：

- 代码层的“更新订单逻辑”已经能跑
- 现在更像是“通知链路没到后端”而不是“到后端后更新失败”

如果你继续排查，建议按这个顺序看：

1. 本地服务是否真的在跑
2. 穿透工具是否在线
3. 支付宝沙箱后台里配置的 `notify_url` 是否和代码一致
4. 本地日志里有没有 `支付回调，消息接收` 这条日志
5. 如果回调有进来但没更新，再查验签和 SQL

## 7. 总结

这个项目实现的是一个完整的 DDD 风格支付和登录系统：

- 登录侧完成了微信扫码登录
- 支付侧完成了支付宝下单、回调、补偿、关单
- 领域层负责业务流程
- 仓储层负责数据库和对象转换
- 触发层负责 HTTP 和定时任务
- 基础设施层负责第三方调用和持久化

这次最关键的不是“有没有下单能力”，而是“支付回调是否真正打进来”。  
从当前日志看，代码里的补偿任务已经在运行，但支付宝异步通知没有形成完整闭环，所以本地状态没有变。
