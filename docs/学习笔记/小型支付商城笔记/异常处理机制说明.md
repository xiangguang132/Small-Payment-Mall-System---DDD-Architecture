# 异常处理机制说明

## 这次讨论的问题

这次主要围绕三个问题：

1. 为什么原来代码里很多地方使用 `IllegalArgumentException`？
2. 为什么改造时使用 `AppException`，而不是直接使用 `GlobalExceptionHandler`？
3. 生产级项目里的异常处理通常应该怎么分层？

## AppException 和 GlobalExceptionHandler 的区别

`AppException` 是业务异常类型。它应该出现在业务代码里，用来主动表达一个可预期的业务失败。

例如：

```java
throw new AppException(ResponseCode.NOT_FOUND, "原料不存在");
throw new AppException(ResponseCode.CONFLICT, "原料编码已存在");
throw new AppException(ResponseCode.UNPROCESSABLE_ENTITY, "原料未启用，不能使用");
```

它的作用是告诉上层：

- 这里不是系统崩溃，而是业务规则不满足。
- 这个错误应该返回什么业务码。
- 这个错误应该给前端展示什么提示。

`GlobalExceptionHandler` 是全局异常处理器。它不应该被业务代码直接调用，也不应该在 `Service` 或 `Repository` 中 import 后手动使用。

它的作用是由 Spring 自动触发：

```text
Controller 调用 Service
        ↓
Service 抛出 AppException
        ↓
异常继续向外抛
        ↓
Spring 捕获异常
        ↓
GlobalExceptionHandler.handleAppException 自动处理
        ↓
返回统一 Response
```

所以二者不是替代关系，而是协作关系：

```text
AppException：业务代码主动抛，携带业务码和错误信息
GlobalExceptionHandler：Web 层统一接住，转换成 HTTP 状态码和 Response
```

## 为什么不是依赖问题

这不是 `GlobalExceptionHandler` 引入不进去的问题。

从分层职责看，`GlobalExceptionHandler` 位于 `trigger` 模块，属于接口层。它依赖 Spring Web，并且负责处理 HTTP 请求中的异常。

`MaterialService` 位于 `domain` 模块，属于领域层。领域层不应该依赖接口层，否则会形成反向依赖：

```text
错误方向：
domain -> trigger
```

正确方向应该是：

```text
trigger -> domain -> infrastructure
```

因此领域层可以抛 `types` 模块里的通用异常 `AppException`，但不应该知道 `GlobalExceptionHandler` 的存在。

## IllegalArgumentException 的问题

`IllegalArgumentException` 是 Java 标准异常，含义是方法参数非法。

它可以用来表达：

```java
throw new IllegalArgumentException("原料id不能为空");
```

但它的问题是语义太粗。比如下面这些错误本质不同：

```text
原料id不能为空       -> 参数校验失败，适合 422
原料不存在          -> 资源不存在，适合 404
原料编码已存在      -> 资源冲突，适合 409
原料未启用不能使用  -> 业务状态不允许，适合 422
```

如果全部使用 `IllegalArgumentException`，`GlobalExceptionHandler` 只能统一处理成一种响应，很难区分业务含义。

使用 `AppException` 后，可以明确表达业务语义：

```java
throw new AppException(ResponseCode.UNPROCESSABLE_ENTITY, "原料id不能为空");
throw new AppException(ResponseCode.NOT_FOUND, "原料不存在");
throw new AppException(ResponseCode.CONFLICT, "原料编码已存在");
```

## 这次 Material 链路的改造原则

Material 相关异常按以下规则处理：

| 场景 | ResponseCode | HTTP 状态 |
| --- | --- | --- |
| 请求对象为空 | `UNPROCESSABLE_ENTITY` | 422 |
| id 为空 | `UNPROCESSABLE_ENTITY` | 422 |
| 编码为空 | `UNPROCESSABLE_ENTITY` | 422 |
| 名称为空 | `UNPROCESSABLE_ENTITY` | 422 |
| 状态值非法 | `UNPROCESSABLE_ENTITY` | 422 |
| 原料不存在 | `NOT_FOUND` | 404 |
| 原料类型不存在 | `NOT_FOUND` | 404 |
| 原料编码已存在 | `CONFLICT` | 409 |
| 原料已删除、未启用 | `UNPROCESSABLE_ENTITY` | 422 |

对应代码风格：

```java
if (material == null) {
    throw new AppException(ResponseCode.UNPROCESSABLE_ENTITY, "原料信息不能为空");
}

if (current == null) {
    throw new AppException(ResponseCode.NOT_FOUND, "原料不存在");
}

if (currentId == null || !currentId.equals(existed.getId())) {
    throw new AppException(ResponseCode.CONFLICT, "原料编码已存在");
}
```

## GlobalExceptionHandler 应该做什么

`GlobalExceptionHandler` 的职责是统一把异常转换成接口响应。

它应该处理几类异常：

```text
AppException
    业务代码主动抛出的业务异常。

DuplicateKeyException
    数据库唯一键冲突，通常作为并发或漏校验兜底。

HttpMessageNotReadableException
MethodArgumentTypeMismatchException
MissingServletRequestParameterException
    请求 JSON 格式错误、参数类型错误、缺少参数。

MethodArgumentNotValidException
BindException
ConstraintViolationException
    @Valid、@NotNull、@NotBlank 等参数校验失败。

Exception
    未预期系统异常兜底，返回 500。
```

业务代码不要这样写：

```java
// 不推荐
globalExceptionHandler.handleAppException(...);
```

业务代码应该这样写：

```java
// 推荐
throw new AppException(ResponseCode.NOT_FOUND, "原料不存在");
```

## 生产级异常处理通常怎么做

生产级项目一般会把异常分成几类。

### 1. 参数校验异常

来源通常是 Controller 入参校验。

例如：

```java
@NotNull(message = "原料id不能为空")
private Long id;
```

这类异常通常返回：

```text
HTTP 400 或 422
业务码：ILLEGAL_PARAMETER 或 UNPROCESSABLE_ENTITY
```

如果是 JSON 格式错误、类型转换失败，通常更接近 `400 Bad Request`。

如果是字段格式正确，但业务校验不通过，通常更接近 `422 Unprocessable Entity`。

### 2. 业务异常

这是业务规则主动拒绝。

例如：

```text
库存不足
订单状态不允许取消
原料未启用
请求号重复
```

这类异常应该使用业务异常类，比如本项目的 `AppException`。

常见响应：

```text
资源不存在 -> 404
资源冲突 -> 409
业务状态不允许 -> 422
权限不足 -> 403
未登录 -> 401
```

### 3. 基础设施异常

来源通常是数据库、Redis、MQ、第三方接口。

例如：

```text
数据库连接失败
Redis 超时
MQ 发送失败
支付宝接口不可用
```

这类异常不要直接把底层错误信息返回给前端。通常做法是：

- 日志里记录完整异常堆栈。
- 对外返回稳定的错误码和通用提示。
- 必要时包装成 `AppException(ResponseCode.SERVICE_UNAVAILABLE, "...")`。

### 4. 并发和唯一约束异常

即使 Service 层提前校验了唯一性，也不能完全避免并发问题。

例如两个请求同时创建同一个原料编码：

```text
请求 A 查询：编码不存在
请求 B 查询：编码不存在
请求 A 插入成功
请求 B 插入失败，数据库唯一索引冲突
```

所以生产级系统一般是：

```text
Service 层先查重，给出友好业务提示
数据库唯一索引兜底，保证数据绝对不重复
GlobalExceptionHandler 捕获 DuplicateKeyException，返回 409
```

### 5. 未预期系统异常

所有没被识别的异常，最后由：

```java
@ExceptionHandler(Exception.class)
```

统一兜底。

这类异常应该：

- 返回 HTTP 500。
- 前端只看到通用提示，比如“未知失败”。
- 后端日志记录完整堆栈。
- 生产环境不要把 SQL、堆栈、服务器路径直接暴露给前端。

## 分层里的异常建议

### Controller 层

Controller 主要做：

- 接收请求。
- 触发 `@Valid` 参数校验。
- 调用 Service。
- 包装成功响应。

Controller 不建议写大量业务判断。可以做很薄的空结果转换，但更推荐让 Service 明确表达业务结果。

### Assembler 层

Assembler 主要做对象转换。

如果输入对象为空，可以抛：

```java
throw new AppException(ResponseCode.UNPROCESSABLE_ENTITY, "原料信息不能为空");
```

如果转换详情时源对象为空，可以抛：

```java
throw new AppException(ResponseCode.NOT_FOUND, "暂无相关原料详情");
```

### Domain Service 层

Domain Service 是业务规则最集中的地方。

这里最适合抛 `AppException`：

```java
throw new AppException(ResponseCode.CONFLICT, "原料编码已存在");
throw new AppException(ResponseCode.NOT_FOUND, "原料类型不存在");
throw new AppException(ResponseCode.UNPROCESSABLE_ENTITY, "原料类型未启用，不能使用");
```

### Repository 层

Repository 更偏数据访问。

它可以做基本防御式校验，例如入参不能为 null：

```java
throw new AppException(ResponseCode.UNPROCESSABLE_ENTITY, "原料id不能为空");
```

但 Repository 不建议承载太多业务语义。比如“原料未启用不能使用”这种判断更适合放在 Service。

## 项目后续改造建议

不要一次性把全项目所有 `IllegalArgumentException` 全部机械替换。

更稳妥的顺序是按业务模块逐个改：

1. Material 原料模块。
2. MaterialType 原料分类模块。
3. MaterialStock 原料库存模块。
4. Product 商品模块。
5. ProductType 商品分类模块。
6. Warehouse 和 WarehouseStock 仓库库存模块。
7. ProductionOrder 生产需求单模块。

每个模块改造时保持同一套规则：

```text
参数为空/格式非法 -> UNPROCESSABLE_ENTITY
资源不存在 -> NOT_FOUND
唯一冲突/重复提交 -> CONFLICT
状态不允许 -> UNPROCESSABLE_ENTITY
权限问题 -> FORBIDDEN 或 NO_LOGIN
系统未知失败 -> UN_ERROR
```

这样改出来的异常体系会更清楚，也更接近生产项目的处理方式。
