# 普通支付流程梳理

## 一、整体流程图

```
┌─────────────────────────────────────────────────────────────────┐
│ ① 锁单/下单                                                      │
│    MarketTradeController.lock_pay_order                          │
│    └→ AbstractOrderService.createOrder()                         │
│       1. 查未支付订单（幂等：存在则复用）                            │
│       2. productPort → ProductRPC 查询商品信息                     │
│       3. doSaveOrder → OrderRepository 保存订单（CREATE）          │
│       4. doPrepayOrder → 调支付宝生成支付表单                       │
│          → 更新订单状态为 PAY_WAIT，返回 payUrl                    │
└─────────────────────────────────────────────────────────────────┘
                          ↓ 用户在支付宝完成支付
┌─────────────────────────────────────────────────────────────────┐
│ ② 支付宝回调                                                     │
│    AliPayController.pay_notify                                   │
│    1. 验签（RSA256）                                             │
│    2. trade_status == TRADE_SUCCESS 时                           │
│    3. alipayNotifyTaskService.saveNotifyTask(params)             │
│       → 按 outTradeNo + tradeNo 去重，写入通知任务表（status=0）    │
└─────────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────────┐
│ ③ 异步消费（规则链处理）                                          │
│    MQ Listener → AlipayNotifyTaskService.processTask(outTradeNo) │
│    1. 加分布式锁 alipayPort.tryLock                              │
│    2. 规则链执行：                                                │
│       TaskExists → TaskStatus → DirectOrder → GroupBuyOrder      │
│                                                                │
│    DirectOrderFilter（普通订单节点）：                              │
│       → orderService.changeOrderPaySuccess(outTradeNo)          │
│         → OrderRepository 更新状态 → PAY_SUCCESS                 │
│       → alipayNotifyTaskRepository.updatedSuccess（status=1）     │
│    3. 异常时更新重试次数（retry_count），超 5 次标记失败             │
│    4. finally 释放锁                                             │
└─────────────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────────┐
│ ④ 退单                                                          │
│    MarketTradeController.refund_order                            │
│    └→ OrderService.refundOrder(userId, outTradeNo)               │
│       1. 查订单 + 归属校验（userId 匹配）                         │
│       2. 已支付（PAY_SUCCESS / DEAL_DONE）：                      │
│          → changeOrderRefunding（乐观锁 CAS → REFUNDING）        │
│          → alipayRefundPort.refund() 调支付宝退款                 │
│          → 成功：REFUNDING → REFUND                              │
│          → 失败：REFUNDING → 原状态（允许重试）                    │
│       3. 未支付（PAY_WAIT / CREATE）：                            │
│          → changeOrderPayClose 直接关单                           │
└─────────────────────────────────────────────────────────────────┘
```

## 三、订单状态流转

```
CREATE → PAY_WAIT → PAY_SUCCESS → REFUNDING → REFUND
                ↘ 超时关单        ↘ 未支付退单
```

| 状态 | 含义 | 触发时机 |
|---|---|---|
| CREATE | 已创建，未发起支付 | doSaveOrder 保存订单 |
| PAY_WAIT | 已生成支付宝支付单，等待用户支付 | doPrepayOrder 调支付宝后 |
| PAY_SUCCESS | 已支付成功 | 支付宝回调 → DirectOrderFilter |
| REFUNDING | 退款中 | refundOrder 发起支付宝退款时 |
| REFUND | 已退款 | 支付宝退款成功回调 |

## 四、关键设计说明

### 4.1 锁单 vs 下单

`lock_pay_order` 接口名面向前端语义（"锁定一个待支付订单"），后端实际调用的是 `createOrder`。

**当前没有真正的锁库存逻辑**，"锁"靠幂等实现：
- 已有 `CREATE` 状态订单 → 补创建支付单
- 已有 `PAY_WAIT` 状态订单 → 直接返回原 payUrl
- 无未支付订单 → 新建订单 + 创建支付单

### 4.2 支付回调异步处理

支付宝回调不直接更新订单状态，而是：
1. 验签后写入 `alipay_notify_task` 表（status=0）
2. MQ 异步消费，通过规则链处理
3. 加分布式锁防并发，异常重试（最多 5 次）

好处：解耦支付回调与业务处理，支持重试，防止 MQ 死循环。

### 4.3 退单设计

- **已支付**：乐观锁 CAS（`changeOrderRefunding`）防并发退款，失败可回滚重试
- **未支付**：直接关单，不涉及资金操作
- **归属校验**：userId 必须匹配，防止越权退他人订单

### 4.4 TODO：库存管理

当前商品无库存数量概念（只有上下架），暂不需要锁库存。后续如需支持限量商品/秒杀，建议拆分为：

```
lockOrder()   → 校验库存 → 冻结库存 → 创建订单
payOrder()    → 调支付宝
notifyCallback() → 确认扣减库存
```
