# 支付宝回调与通知-技术复用方案

更新日期：2026-08-14

## 1. 背景

`s-pay-mall-ddd-cc` 当前已经不是一个单纯的“微信公众号扫码登录 + 支付宝模拟支付”项目，而是逐步扩展成包含原料采购、生产、商品、库存、销售、普通购买与拼团的一体化项目。

参考项目 `group-buy-market` 中的拼团回调任务实现具备很好的可靠性设计，包括：

- 任务表持久化
- 状态机流转
- 立即执行 + 定时补偿
- Redis 分布式锁防重复
- 失败重试

这些技术本身不依赖“第三方业务系统”。因此，本项目可以放弃成团后主动回调外部 `notify_url` 的设计，把同一套技术复用到支付宝支付回调处理中。

## 2. 要解决的问题

当前支付宝回调链路仍不完整：

1. `AliPayController.payNotify` 只做验签，然后直接调用 `orderService.changeOrderPaySuccess`。
2. 普通订单和拼团订单没有统一分叉。
3. 支付宝回调可能重复，当前缺少可靠的幂等与任务补偿机制。
4. 拼团结算服务已经存在，但支付宝回调还没有调用 `GroupBuySettlementService.settlementGroupBuyOrder`。
5. `pay_order` 的商户订单号已统一为 `out_trade_no`，但支付单没有直接保存 `activityId`、`teamId`，拼团关联需要通过 `group_buy_order.out_trade_no` 反查。

目标是把“支付宝回调”也改成可靠任务链路：

```text
支付宝回调
  -> 验签
  -> 写入支付通知任务
  -> 返回 success
  -> 立即处理
  -> 定时补偿
  -> 分布式锁防重复
```

## 3. 两个 notify_url 的区别

本项目中存在两个 `notify_url`，含义完全不同：

| 字段 | 方向 | 含义 | 本项目是否保留 |
| --- | --- | --- | --- |
| `group_buy_team.notify_url` | 本系统 -> 外部业务系统 | 成团后主动通知外部业务方 | 当前一体化项目可以不保留 |
| `alipay.notify_url` | 支付宝 -> 本系统 | 支付宝支付结果回调地址 | 必须保留 |

本文只复用参考项目的“任务 + 补偿 + 锁 + 状态机”技术，不再继续实现 `group_buy_team.notify_url` 对应的外部业务回调。

## 4. 目标架构

```text
支付宝
  -> POST alipay.notify_url
  -> AliPayController.payNotify
  -> 验签
  -> 写入 alipay_notify_task
  -> 返回 success

AlipayNotifyTaskService
  -> 立即处理任务
  -> 定时任务扫描 status in (0, 2)
  -> Redis 分布式锁
  -> 根据 orderType 分叉：
       - 普通订单 -> changeOrderPaySuccess
       - 拼团订单 -> GroupBuySettlementService.settlementGroupBuyOrder
  -> 更新任务状态
```

## 5. 任务表设计

建议新增 `alipay_notify_task`，避免和参考项目的 `notify_task` 语义混淆。

```sql
CREATE TABLE alipay_notify_task (
    id             BIGINT AUTO_INCREMENT PRIMARY KEY,
    out_trade_no   VARCHAR(64)  NOT NULL,
    trade_no       VARCHAR(64)  NOT NULL DEFAULT '',
    order_type     TINYINT      NOT NULL DEFAULT 0 COMMENT '0-普通订单 1-拼团订单',
    task_status    TINYINT      NOT NULL DEFAULT 0 COMMENT '0-待处理 1-成功 2-重试 3-失败',
    retry_count    INT          NOT NULL DEFAULT 0,
    parameter_json TEXT,
    create_time    DATETIME     NOT NULL,
    update_time    DATETIME     NOT NULL,
    UNIQUE KEY uq_out_trade_no_trade_no (out_trade_no, trade_no)
);
```

`parameter_json` 保存支付宝回调中的关键参数，例如：

```json
{
  "out_trade_no": "2026081400000001",
  "trade_no": "202608142200100001",
  "trade_status": "TRADE_SUCCESS",
  "total_amount": "99.00",
  "gmt_payment": "2026-08-14 12:00:00"
}
```

唯一键用于幂等，避免同一个支付宝交易被重复处理。

## 6. 任务状态机

```text
0：待处理
1：处理成功
2：需要重试
3：处理失败
```

建议流转规则：

| 处理结果 | 状态更新 |
| --- | --- |
| 处理成功 | `task_status = 1`，`retry_count + 1` |
| 业务处理失败且 `retry_count < 5` | `task_status = 3`，`retry_count + 1` |
| 业务处理失败且 `retry_count >= 5` | `task_status = 2`，`retry_count + 1` |
| 获取不到锁 | 不更新状态，下一轮继续 |
| 参数异常或重复任务 | 按已处理处理，不重复执行业务 |

如果希望状态语义更直观，也可以调整为：

```text
3：普通失败，等待定时任务重试
2：超过最大重试次数，最终失败
```

## 8. 关键流程

### 8.1 支付宝回调入口

```text
1. 获取支付宝请求参数
2. 验签
3. 验签失败 -> 返回 false
4. 验签通过 -> 查询或创建 alipay_notify_task
5. 已存在且 task_status = 1 -> 直接返回 success
6. 不存在 -> 插入 task_status = 0
7. 返回 success
```

支付宝回调入口只做“验签 + 落任务”，不执行重业务逻辑，避免回调超时。

### 8.2 任务处理服务

```text
1. 查询 task_status in (0, 2)
2. 遍历任务
3. 获取 Redis 锁
4. 拿不到锁 -> 跳过，下一轮再处理
5. 拿到锁：
   - 解析 parameter_json
   - 普通订单 -> orderService.changeOrderPaySuccess
   - 拼团订单 -> groupBuySettlementService.settlementGroupBuyOrder
   - 成功 -> task_status = 1
   - 失败 -> 按重试规则更新状态
6. finally 中判断锁仍由当前线程持有，再释放
```

分布式锁 key 建议：

```text
alipay_notify_lock_<outTradeNo>
```

## 9. 幂等与并发控制

支付宝可能重复发送同一笔交易的回调，也可能多个实例同时处理同一任务。因此需要同时处理：

1. 数据库唯一键：`out_trade_no + trade_no`
2. 任务状态校验：已经成功的不再执行
3. Redis 分布式锁：防止同一 `outTradeNo` 并发处理
4. 业务侧幂等：拼团结算、订单更新都需要支持重复调用

当前 `changeOrderPaySuccess` 和 `GroupBuySettlementService` 需要确认重复回调时不会破坏数据。

## 10. 与 NoPayNotifyOrderJob 的关系

`NoPayNotifyOrderJob` 仍然保留，作用是主动查询支付宝，防止漏掉回调。

两者互补：

| 机制 | 作用 |
| --- | --- |
| 支付宝主动回调 | 实时收到支付结果 |
| `NoPayNotifyOrderJob` | 防止支付宝回调丢失 |
| `AlipayNotifyJob` | 补偿支付通知任务处理失败 |

## 11. 实施顺序

1. 以 `pay_order.out_trade_no` 作为支付回调的关联键，增加按 `outTradeNo` 查询拼团关联的能力，不向 `pay_order` 冗余复制 `activityId`、`teamId`。

   关联查询建议按以下链路实现：

   - `pay_order` 已把 `order_id` 改为 `out_trade_no`，支付回调只依赖 `out_trade_no` 查询普通订单。
   - `group_buy_order` 已保存 `out_trade_no`、`activity_id`、`team_id`，用 `out_trade_no` 反查拼团关联。
   - 若通知任务只持有 `outTradeNo`，推荐先调用 `queryPayOrderByOutTradeNo(outTradeNo)` 拿到 `userId`、`orderType`，再调用 `queryGroupBuyOrderByOutTradeNo(userId, outTradeNo)` 获取 `activityId`、`teamId`。这样可以复用现有查询和结算链，不需要新增无 `userId` 的查询入口；只有未来确认拼团订单不写 `pay_order` 时，才考虑新增仅按 `outTradeNo` 查询 `group_buy_order` 的方法。
   - 任务处理按 `orderType` 分叉时，将 `userId`、`outTradeNo`、`payTime` 组装为 `GroupBuySettlementCommandEntity`，交给拼团结算服务。
2. 新增 `alipay_notify_task` 建表 SQL、PO、DAO、Mapper。
3. 新增 `AlipayNotifyTaskEntity` 和 `IAlipayNotifyTaskRepository`。
4. 新增 `AlipayNotifyTaskService`，包含任务状态机和分布式锁。
5. 修改 `AliPayController.payNotify`，只负责验签和落任务。
6. 新增 `AlipayNotifyJob` 定时补偿任务。
7. 在任务处理中按 `orderType` 分叉普通订单和拼团订单。
8. 补充单元测试与接口测试。

## 12. 验收标准

- 支付宝回调验签通过后能快速返回 `success`。
- `alipay_notify_task` 会写入待处理任务。
- 普通订单能通过任务服务完成支付成功更新。
- 拼团订单能通过任务服务触发拼团结算。
- 重复回调不会重复更新订单或重复结算。
- 多实例不会并发处理同一个 `outTradeNo`。
- 处理失败后定时任务能继续补偿。
- 项目编译和测试通过。

## 13. 当前明确不做的部分

当前一体化项目暂不实现：

- `group_buy_team.notify_url` 外部业务回调
- `GroupBuyNotifyPort` 主动通知第三方业务系统
- 成团后跨服务 HTTP 通知

如果以后拆成独立服务，再把 `alipay_notify_task` 泛化成通用 outbox，增加事件类型和目标服务，不需要推翻当前设计。
