# 商品列表页性能优化

## 问题现象

商品分页接口 `GET /api/v1/product/page` 响应速度很慢，列表加载卡顿。

## 根因分析

### 后端（主要瓶颈）

#### 1. N+1 查询问题

`ProductController.toDetailListWithActivity()` 中，对分页返回的每个商品逐个查询 `group_buy_activity` 表：

```java
// 改动前：每个商品单独查一次活动表
for (ProductAggregate product : products) {
    GroupBuyActivityEntity activity = groupBuyActivityRepository
        .queryGroupBuyActivityByProductId(product.getId()); // N+1!
}
```

12 条商品 = 12 次额外 DB 查询，加上分页查询本身 = **13 次 DB 查询/页**。

#### 2. Trial 试算链路过重

有拼团活动的商品，每个都走完整的试算链路（`RootNode → SwitchNode → MarketNode`），内部包含：

```
trialService.queryGroupBuyTrial()
  └─ SwitchNode: 降级检查、切量判断
  └─ MarketNode:
       productRepository.queryById()         // DB 查询（重复，列表已有）
       activityRepository.queryByActivityId() // DB 查询（重复，刚查过）
       discountRepository.queryDiscountById() // DB 查询
       trialRuleChain.execute()               // 规则链计算
```

假设 12 个商品中 5 个有拼团活动，每个活动 3+ 次 DB 查询 = 额外 **15+ 次 DB 查询**。

**合计：一次分页请求 = 26~38 次数据库查询。**

#### 3. 响应体臃肿

返回的 `ProductDetailResponse` 包含 15 个字段（`description`、`sku`、`categoryDescription`、`imgs`、`createTime`、`updateTime` 等），列表页完全用不到。SQL 同样 SELECT 了 14 列并 LEFT JOIN `product_type` 表。

### 前端（次要问题）

- `<img>` 未设置 `loading="lazy"`，12 张图片同时发起请求
- `hasMore` 判断用 `list.length === PAGE_SIZE`，最后一页恰好 12 条时会多发一次空请求

## 优化方案与改动

### 1. 批量查询替代 N+1

将逐个查询改为 `IN` 批量查询 + `Map` 关联：

```java
// 改动后：一次批量查询，Map 关联
List<Long> productIds = products.stream()
    .map(ProductAggregate::getId).collect(Collectors.toList());

Map<Long, GroupBuyActivityEntity> activityMap = groupBuyActivityRepository
    .queryGroupBuyActivityByProductIds(productIds)  // 1 次批量查询
    .stream()
    .collect(Collectors.toMap(GroupBuyActivityEntity::getProductId,
        Function.identity(), (a, b) -> a));
```

**效果：12 次活动查询 → 1 次批量查询。**

涉及文件：

| 文件 | 改动 |
|---|---|
| `IGroupBuyActivityDao.java` | 新增 `queryByProductIds(List<Long>)` |
| `group_buy_activity_mapper.xml` | 新增 `IN` 批量查询 SQL |
| `IGroupBuyActivityRepository.java` | 新增 `queryGroupBuyActivityByProductIds()` |
| `GroupBuyActivityRepository.java` | 实现批量方法，抽取 `toEntity()` 复用 |

### 2. 去掉列表页 Trial 试算

列表页只返回原价 + `activityId` + `targetCount`，试算折后价延迟到商品详情页获取。

```java
// 改动前：每个有活动的商品都做完整试算
GroupBuyTrialResult trial = groupBuyTrialService.queryGroupBuyTrial(...);
resp.setTrialPayPrice(trial.getPayPrice());

// 改动后：直接从活动实体取 targetCount，不做试算
item.setActivityId(activity.getActivityId());
item.setTargetCount(activity.getTargetCount());
```

**效果：每个有活动的商品省去 3+ 次 DB 查询和规则链计算。**

涉及文件：

| 文件 | 改动 |
|---|---|
| `ProductController.java` | 移除 `IGroupBuyTrialService` 调用，`targetCount` 直接从 activity 获取 |
| `ProductCard.tsx` | `hasGroupBuy` 从 `trialPayPrice != null` 改为 `activityId != null` |

### 3. 精简响应体

新增轻量 DTO `ProductListItemResponse`（6 字段），替换列表页使用的 `ProductDetailResponse`（15 字段）：

```java
// 新增精简 DTO
@Data
public class ProductListItemResponse {
    private Long id;
    private String name;
    private BigDecimal price;
    private String coveringImg;
    private Long activityId;
    private Integer targetCount;
}
```

同时 SQL 从 14 列 SELECT + LEFT JOIN 精简为 4 列无 JOIN：

```sql
-- 改动前
SELECT p.id, p.name, p.description, p.sku, p.category_id,
       pt.name as category_name, pt.description as category_description,
       pt.type_code as category_code, p.status, p.price,
       p.covering_img, p.is_del, p.create_time, p.update_time
FROM product p
LEFT JOIN product_type pt ON p.category_id = pt.id

-- 改动后
SELECT p.id, p.name, p.price, p.covering_img
FROM product p
```

涉及文件：

| 文件 | 改动 |
|---|---|
| 新增 `ProductListItemResponse.java` | 精简列表响应 DTO |
| `product_mapper.xml` | `queryPage`/`querySearch` 只查 4 列，去掉 JOIN |
| `ProductController.java` | `page()`/`search()` 返回 `ProductListItemResponse` |

### 4. 前端优化

| 改动 | 文件 | 效果 |
|---|---|---|
| `<img loading="lazy">` | `ProductCard.tsx` | 非视口图片延迟加载，减少并发请求数 |
| `hasMore` 用 `total` 精确判断 | `product/page.tsx`、`page.tsx` | 避免最后一页多发一次空请求 |
| 新增 `ProductListItem` 类型 | `types/index.ts` | 前端类型与精简 DTO 对齐 |
| 卡片去掉 `categoryName` 展示 | `ProductCard.tsx` | 配合后端精简 |

## 优化效果

| 指标 | 改动前 | 改动后 |
|---|---|---|
| 每页 DB 查询次数 | 26~38 次 | **2 次** |
| 每条响应 JSON 字段数 | 15 个 | **6 个** |
| SQL SELECT 列数 | 14 列 + JOIN | **4 列，无 JOIN** |
| 图片加载策略 | 全部 eager | **lazy（视口外延迟）** |
| 空请求问题 | 最后一页可能多发 1 次 | **无** |

## 后续可优化方向

- **前端缓存层**：引入 SWR / React Query，避免页面来回切换时重复请求
- **接口缓存**：商品列表是读多写少场景，可在 Service 层加 Redis 缓存，设置短 TTL（如 30s）
- **数据库索引**：确保 `product(is_del, id DESC)` 和 `group_buy_activity(product_id, status)` 有合适索引
