# 超时订单扫描任务问题分析与修复记录

## 一、背景与现象

支付模块的 `TimeoutOrderJob` 每分钟（cron `0 */1 * * * ?`）触发一次，负责处理三类超时：

- 普通订单未支付超时 → 关单
- 普通订单已支付超时 → 支付宝退款
- 拼团订单超时 → 退款关团

现象：日志里每隔一分钟刷一批错误，例如：

```
ERROR AlipayRefundPort - 支付宝退款失败 outTradeNo:06487134927043
ERROR OrderService     - 超时退款：支付宝退款失败 outTradeNo=06487134927043
INFO  TimeoutOrderJob  - 超时任务：处理失败，跳过 outTradeNo=06487134927043
```

涉及的订单都是**同一个 out_trade_no 反复重试**，且同一时间段有 10 笔 PAY_SUCCESS 的测试单在同时刷错误。

## 二、问题定位

### 2.1 任务扫描了哪些表

`TimeoutOrderJob` 通过两个 Provider 拿到待处理的 out_trade_no 列表：

| Provider | 扫描表 | 语句 |
|---|---|---|
| `CloseOrderTimeoutTaskProvider` | `pay_order` | `queryTimeOutCloseOrderList` / `queryNoPayNotifyOrder` |
| `GroupBuyRefundTimeoutTaskProvider` | `group_buy_order` + `group_buy_team` | `queryTimeOutRefundOrderList` |

### 2.2 原始 SQL 的三个问题

**① 非 sargable 条件（列被包进表达式，索引用不上范围过滤）**

```sql
-- 改前：order_time 在表达式右侧，MySQL 无法用索引做范围过滤
SELECT out_trade_no FROM pay_order
WHERE status IN ('PAY_WAIT', 'PAY_SUCCESS') AND NOW() >= order_time + INTERVAL 15 MINUTE
ORDER BY id ASC LIMIT 50;
```

**② 表上没有匹配索引**

- `pay_order` 只有 PK、`uq_order_id(out_trade_no)`、`idx_user_id_product_id`
- 没有 `(status, order_time)` 索引 → WHERE 只能**全表扫描**

**③ 拼团 SQL 没有 ORDER BY / LIMIT**

```sql
-- 改前：一次性把过期单全捞回来，量大了直接爆内存、拖垮任务
select o.out_trade_no
from group_buy_order o
left join group_buy_team t on o.team_id = t.team_id
where (
    (o.status = 0 and o.create_time < date_sub(now(), interval 15 minute))
    or
    (o.status = 1 and t.status = 0 and t.valid_end_time < now())
);
```

### 2.3 结论：量小看不出，量大是硬伤

- 应用层有 `LIMIT` 兜底，不会把全表 load 进内存；
- 但**数据库层每次都是全表扫描**：每轮只为了拿 ≤50 条结果，却把整张订单表（几万~几十万行）完完整整走一遍；
- 支付宝侧又因为这些测试单**交易不存在**（`ACQ.TRADE_NOT_EXIST`）或沙箱网关 **504** 永远退不了款，于是每分钟全表扫 + 每分钟重试失败，形成无意义的循环。

## 三、修复方案

### 3.1 补索引（DDL）

```sql
ALTER TABLE pay_order       ADD INDEX idx_status_order_time (status, order_time);
ALTER TABLE group_buy_order ADD INDEX idx_status_create_time (status, create_time);
```

### 3.2 改写为 sargable 条件（核心）

核心思路一句话：**让参与比较的列单独出现在左边，常量/表达式放右边**。

等价变换：`NOW() >= order_time + INTERVAL 15 MINUTE` ⟺ `order_time <= DATE_SUB(NOW(), INTERVAL 15 MINUTE)`

```sql
-- queryTimeoutCloseOrderList（改后）
SELECT out_trade_no as outTradeNo FROM pay_order
WHERE status IN ('PAY_WAIT', 'PAY_SUCCESS') AND order_time <= DATE_SUB(NOW(), INTERVAL 15 MINUTE)
ORDER BY order_time ASC LIMIT 50;

-- queryNoPayNotifyOrder（改后）
SELECT out_trade_no as outTradeNo FROM pay_order
WHERE status = 'PAY_WAIT' AND order_time <= DATE_SUB(NOW(), INTERVAL 1 MINUTE)
ORDER BY order_time ASC LIMIT 10;
```

### 3.3 统一 ORDER BY 与 LIMIT（与索引同序 + 分批）

`ORDER BY id ASC` → `ORDER BY order_time ASC`，和 `idx_status_order_time` 天然同序，减少一次排序；拼团 SQL 补上分批：

```sql
-- queryTimeOutRefundOrderList（改后，末尾追加）
order by o.create_time asc
limit 50;
```

### 3.4 修改的文件

- `s-pay-mall-ddd-app/src/main/resources/mybatis/mapper/pay_order_mapper.xml`
- `s-pay-mall-ddd-app/src/main/resources/mybatis/mapper/group_buy_order_mapper.xml`

> ⚠️ 注意：`target/classes/` 里是旧资源，**需重新构建**（build / `mvn compile`）后才生效。

## 四、验证

用 EXPLAIN 对比改后条件，可证明索引路径可用：

```sql
-- 改后条件 + 强制走新索引
EXPLAIN SELECT out_trade_no FROM pay_order FORCE INDEX (idx_status_order_time)
WHERE status IN ('PAY_WAIT','PAY_SUCCESS') AND order_time <= DATE_SUB(NOW(), INTERVAL 15 MINUTE)
ORDER BY order_time ASC LIMIT 50;
```

可以看到：

```
type=range, key=idx_status_order_time, rows=2, Extra: Using index condition
```

- `type=range`：索引范围扫描
- `Using index condition`：`order_time <= ...` 被下推到索引内部，只读"过期的那一小段尾巴"
- 之前是全表扫；现在只扫"该状态下过期的少数单"

**⚠️ 一个预期内的坑**：测试库只有几十行时，优化器会因"全表成本更低"继续选 PRIMARY 全扫（`EXPLAIN` 看不到索引生效）。**这不是没效果**，是优化器基于成本的正常选择。等数据量上到几万行，验证计划里自然会出现 `idx_status_order_time`。

## 五、遗留与后续建议

### 5.1 覆盖索引（数据量大后再加，可选）

```sql
-- 让查询不回表，直接索引取 out_trade_no（注意 out_trade_no 本身就是唯一键，属冗余列）
ALTER TABLE pay_order ADD INDEX idx_status_order_time_cov (status, order_time, out_trade_no);
```

### 5.2 治本方案：延迟队列（推荐，量再大也不全表扫）

仓库里已有思路参考：`docs/学习笔记/对接拼团模块笔记/拼团退单-MQ闭环实现方案.md`

- 下单/支付成功时，把 `out_trade_no + 到期时间` 写入延迟队（RabbitMQ 延迟插件 / Redis ZSET / 定时分桶）
- 到期才弹出单条处理，**不再存在"每分钟全表扫"**，扫描任务退化为"到期弹单"

### 5.3 脏数据处理：`ACQ.TRADE_NOT_EXIST` 应视为终态，别再无限重试

支付宝沙箱对历史交易数据保留有限，隔天退款会返回"交易不存在"（`40004 ACQ.TRADE_NOT_EXIST`）。当前 `AlipayRefundPort.refund()` 对「业务性失败」和「瞬时失败（如 504）」统一返回 `false`，导致永远重试。建议对 `TRADE_NOT_EXIST` 这类终态错误直接把订单标记为 REFUND，不再进入每分钟重试循环。

测试环境的 10 笔 PAY_SUCCESS 脏数据可直接清理：

```sql
DELETE FROM pay_order WHERE status = 'PAY_SUCCESS' AND order_time < NOW() - INTERVAL 1 DAY;
```

## 六、小结

| 问题 | 修复 |
|---|---|
| 无 (status, order_time) 索引 → 全表扫描 | 补联合索引 |
| `NOW() >= order_time + INTERVAL` 不可走索引 | 改写为 `order_time <= DATE_SUB(NOW(), INTERVAL x)` |
| `ORDER BY id` 与索引不同序 → filesort | 改为 `ORDER BY order_time ASC` |
| 拼团 SQL 无 LIMIT → 全量捞 | 补 `ORDER BY ... LIMIT 50` |
| 支付宝侧交易不存在仍无限重试 | 终态错误置为 REFUND（建议） |
