# AI拷打-1

## 总体判断

这个项目第一眼会让我觉得：你不是只会 CRUD，至少理解了商城、支付、库存、生产单、DDD 分层这些概念。

但深入追问后，我会怀疑你对“供应链系统的核心复杂度”掌握还不够。这个项目目前更像是在学习型 DDD 模板上扩展功能，真正的工程一致性、幂等、补偿、状态机、审计能力还没有站稳。

如果用一句话评价：

> 有业务闭环，有分层意识，但离生产级供应链系统还差“可靠性证明”。

## 我会直接追问你的问题

### 1. 关于 DDD

你说这是 DDD 项目，那你的聚合根是什么？

生产单是聚合根，还是库存分配单是聚合根？

它们之间的事务边界怎么划分？

为什么生产单服务里可以直接编排原料分配、锁库、出库、成品入库？

这是领域服务、应用服务，还是事务脚本？

如果我让你把 `domain` 模块单独拿出去复用，它能不能脱离 Spring、Web、支付宝、JWT 独立运行？

### 2. 关于库存分配单状态

库存分配单有哪些状态？

每个状态允许哪些操作？

比如：

- 待锁定能不能释放？
- 已锁定能不能再次锁定？
- 已出库能不能释放？
- 释放失败怎么办？
- 出库失败怎么办？

如果 `lock` 被重复调用两次，会发生什么？

如果第一次锁了一半库存后服务宕机，这张分配单处于什么状态？系统如何恢复？

### 3. 关于库存一致性

你用了数据库条件更新防止超卖，这个思路是对的。

但你能不能证明不会出现库存不一致？

比如这个不变量：

```text
available_qty + locked_qty = total_qty
```

这个不变量在哪里保证？

是靠代码自觉，数据库约束，还是库存流水对账？

如果某次更新只成功了一半，怎么修？

如果线上库存数据错了，怎么定位是哪张业务单导致的？

### 4. 关于生产单补偿

生产单执行失败时，你释放已锁定原料，这个方向是对的。

但我会继续问：

如果原料已经自动出库成功，成品入库失败，这时候你还怎么释放？

此时 release 的语义已经不对了，因为原料已经从库存中出去了。

你应该怎么处理？

- 反向入库？
- 生成补偿单？
- 标记待人工处理？
- 通过库存流水回滚？
- 通过任务重试最终一致？

如果这个问题答不清楚，说明你对“分布式业务流程失败后如何收敛”还没有真正建立认知。

### 5. 关于幂等

你为什么用“1 小时内相同生产单”防重复？

如果业务上允许 1 小时内创建两张完全一样的生产单怎么办？

如果用户重复点击，正确的幂等键应该来自哪里？

是前端生成 requestId，后端生成业务单号，还是基于业务唯一约束？

支付回调怎么做幂等？

支付宝重复通知怎么办？

订单金额校验在哪里？

支付成功后数据库更新成功，但消息发送失败怎么办？

### 6. 关于任务调度

定时任务如果部署两台机器，会不会重复执行同一张生产单或分配单？

你是用什么方式避免重复处理？

- 本地锁？
- Redis 分布式锁？
- 数据库状态抢占？
- 任务表分片？
- 乐观锁 version？

如果任务执行失败，重试策略是什么？

最大重试次数是多少？

超过最大重试次数后进入什么状态？

有没有下次重试时间？

有没有人工介入状态？

### 7. 关于安全

配置文件里为什么提交微信密钥、支付宝私钥、JWT secret？

即使是沙箱，这在公司代码库里也是严重问题。

上线前你准备怎么做密钥管理？

- 环境变量？
- 配置中心？
- KMS？
- 密钥轮换？
- 不同环境隔离？

如果密钥已经提交到 Git 历史里，你怎么处理？

### 8. 关于测试

为什么项目没有测试？

供应链项目最核心的是库存并发、状态流转、失败补偿，而这些都需要测试证明。

我会要求你至少说明以下测试怎么写：

- 并发锁库不超卖
- 库存不足时分配失败
- 多库位库存拆分正确
- 锁库成功后释放库存正确
- 自动出库后库存字段正确
- 生产单执行失败后补偿正确
- 重复执行生产单不会重复扣库存
- 支付重复回调不会重复更新订单

如果没有这些测试，我很难相信这个项目的核心链路是可靠的。

## 我会质疑的设计点

### 1. 有分层，但领域模型偏贫血

项目确实按 DDD 拆了模块，但很多聚合对象更像数据载体。

大量业务规则写在 Service 里，状态值用 `0/1/2/3` 这种数字表达。

真正的领域模型应该能表达：

- 当前状态是什么
- 能不能执行某个动作
- 执行动作后状态如何变化
- 哪些业务不变量必须被保护

如果这些规则只是散落在 Service 的 if 判断里，那本质还是事务脚本。

### 2. 库存没有流水，审计能力不足

供应链系统里库存变更必须能追溯。

每一次入库、锁定、释放、出库、调整，都应该有库存流水。

流水至少要记录：

- 业务单号
- 业务类型
- 物料 ID
- 库位
- 变更前数量
- 变更数量
- 变更后数量
- 操作时间
- 操作人或系统来源

现在如果只有当前库存表，线上库存错了，很难查账。

### 3. 缺少业务单据体系

真实供应链里，很多操作不能只是改字段。

入库、出库、调拨、盘点、锁定、释放都应该有对应单据或流水。

否则系统只能“执行动作”，不能“解释动作”。

能执行不等于能运营。

### 4. 缺少 BOM 物料清单

生产一个商品需要哪些原料、比例是多少，应该由 BOM 决定。

当前如果是创建生产单时由请求直接传原料明细，那更像演示流程。

真实系统里应该是：

```text
商品 -> BOM -> 原料需求 -> 库存分配 -> 锁库 -> 出库 -> 成品入库
```

如果没有 BOM，生产单的业务可信度会弱很多。

### 5. 异常状态设计不足

真实系统不会只有成功和失败。

供应链系统更常见的是：

- 待处理
- 处理中
- 部分成功
- 待重试
- 补偿中
- 补偿失败
- 待人工确认
- 已关闭

如果异常状态太粗，线上问题会很难恢复。

### 6. 模块依赖不够干净

领域层应该尽量保持纯粹。

如果 domain 里依赖 Web、JWT、支付宝 SDK，就说明技术细节污染了领域层。

这会导致：

- 领域逻辑难以单测
- 模块复用性变差
- 分层边界模糊
- 后续演进成本变高

### 7. 配置安全严重扣分

密钥、私钥、token、数据库密码不应该提交到仓库。

这类问题在真实公司里不是“小瑕疵”，而是安全事故风险。

哪怕是学习项目，也应该体现基本安全意识。

## 如果你答不好，我会给的评价

你能完成一个多模块 Spring Boot 业务项目，说明基础开发能力合格。

你知道库存扣减要用数据库条件更新，说明有一定并发意识。

你把生产、原料、库存、支付串起来，说明有业务抽象意识。

但你目前对供应链核心问题的理解还偏表层。

项目能演示流程，但不能证明可靠。

真正的大厂后端不会只问接口通不通，而是会问：

- 失败了怎么办？
- 重复了怎么办？
- 并发了怎么办？
- 查账怎么查？
- 数据错了怎么修？
- 多实例部署怎么保证不重复消费？
- 业务状态怎么收敛？

这些问题如果答不清楚，项目就只能算“学习项目”，不能算“工程项目”。

## 最应该优先补强的地方

### 1. 补库存流水

这是供应链系统的核心基础设施。

没有库存流水，就没有审计、对账、追责和修复能力。

### 2. 补状态机

把生产单、库存分配单、支付单的状态流转显式建模。

不要让状态值散落在代码里。

### 3. 补幂等

创建生产单、执行生产单、支付回调、库存分配、锁库、出库都应该有幂等设计。

### 4. 补失败补偿

尤其是生产链路：

```text
锁原料 -> 原料出库 -> 成品入库
```

每一步失败后的状态和补偿策略都要讲清楚。

### 5. 补 BOM

有 BOM 后，这个项目才更像供应链生产系统，而不是“手动传原料的库存演示系统”。

### 6. 补任务抢占和重试

定时任务不能只考虑单机。

要考虑多实例部署下的重复执行、失败重试、最大重试、死信状态。

### 7. 补测试

尤其是并发库存测试和状态流转测试。

这部分是证明你真正理解业务可靠性的关键。

### 8. 清理敏感配置

改成环境变量或配置中心。

提交示例配置，不提交真实密钥。

## 面试时更成熟的表达方式

不要硬说这个项目已经很完整。

更好的说法是：

> 这是我实习期间基于供应链学习做的一个业务闭环项目，重点是理解商城、支付、库存、生产单和 DDD 分层。当前版本能跑通主流程，但我也知道它距离生产级还有差距。后续我会优先补库存流水、状态机、幂等键、任务抢占、Outbox 事件表、BOM 物料清单和并发测试。因为供应链系统最核心的不是接口数量，而是库存数据在并发和异常情况下仍然可信。

这比强行包装项目更可信。

## 最终评价

如果我是面试官，我会给这个项目的评价是：

> 方向选得不错，业务比普通商城 CRUD 更有价值，也能看出你有主动学习供应链和 DDD 的意识。但当前实现还偏学习型，核心可靠性设计不足。你需要把库存一致性、幂等、补偿、状态机、流水、测试这些问题补上，项目含金量才会明显提升。
