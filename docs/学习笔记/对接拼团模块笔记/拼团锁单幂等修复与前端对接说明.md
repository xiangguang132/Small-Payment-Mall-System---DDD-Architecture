# 拼团锁单幂等修复与前端对接说明

> 日期：2026-08-25　分支：group-buy-dev
> 关联接口：`POST /api/v1/groupbuy/lockGroupBuyOrder`

## 一、问题现象

`group_buy_order` 表中出现两条几乎相同的记录（间隔 22 秒），同一用户、同一活动、同一商品，却各自开了一个新团：

| id | order_id | user_id | team_id | activity_id | out_trade_no | create_time |
|----|----------|---------|---------|-------------|--------------|-------------|
| 2 | 553853653256 | oxf0n3aZpX... | 01849553 | 10001 | 10475935537411 | 22:09:37 |
| 3 | 582387148748 | oxf0n3aZpX... | 02205239 | 10001 | 12047459012257 | 22:09:59 |

即：**用户重复点击"发起拼团"，服务端重复创建了拼团订单**，没有幂等保护。

## 二、根因分析

代码里其实已经有一处幂等检查，但它失效了：

```java
// GroupBuyOrderService.lockGroupBuyOrder —— 按 userId + outTradeNo 查重
GroupBuyOrderEntity existing = groupBuyRepository.queryGroupBuyOrderByOutTradeNo(
        aggregate.getUserId(), aggregate.getOutTradeNo());
if (existing != null) return existing;
```

失效原因在 Controller：

```java
// GroupBuyController —— 每次 HTTP 请求都随机生成新的 outTradeNo
String outTradeNo = RandomStringUtils.randomNumeric(14);
```

outTradeNo 每次都是新号 → 查重永远查不到 → 每次点击都插入一条订单；且请求不传 teamId 时还会各开一个新团。

**结论**：`userId + outTradeNo` 这个幂等键组合本身是正确的（与参考项目一致），前提是 outTradeNo 在"同一笔逻辑订单的多次请求"之间保持稳定；此外还缺一层业务防重兜底。

## 三、修复方案（三层防线）

### 第 1 层：重试幂等（userId + outTradeNo）

- 前端首次锁单成功后保存响应中的 `outTradeNo`，同一笔单的重试/重复点击**原样回传**
- 服务端优先使用透传值；为空才生成随机号（兼容旧调用方）
- 命中已有订单直接返回，不再新建

### 第 2 层：业务防重（userId + activityId + status=0）★核心

即使前端不改造（每次都不传 outTradeNo），也不会再出现重复订单：

- 锁单前查询该用户在该活动下是否存在**进行中（待付款 status=0）**的订单
- 存在则直接复用返回该订单（含其原 teamId/outTradeNo/payAmount），不再走规则链、不再插库
- 已退款（status=2）/已成团的订单不受影响，用户付完款或退款后仍可再次参团
- 超时未付款的订单由 15 分钟超时退单任务关闭后自动释放资格

新增查询：

```xml
<!-- group_buy_order_mapper.xml -->
select ... from group_buy_order
where user_id = #{userId} and activity_id = #{activityId} and status = 0
order by id desc limit 1
```

### 第 3 层：支付单落库回归修复

排查中发现历史提交 `67908d1` 误删了 GROUP_BUY 支付单的 insert（只剩 update），导致 **pay_order 表里根本没有拼团支付单记录**，支付宝回调按 out_trade_no 反查会失败。本次一并修复：

- 恢复 `IOrderRepository.saveGroupBuyPayOrder()`（insert，orderType=GROUP_BUY，status=CREATE）
- `createGroupBuyPayOrder()` 改为幂等写法：按 outTradeNo 查不到才插入，随后回写 payUrl 并置为 PAY_WAIT——复用订单/重试时不会重复插入

另注意：Controller 创建支付单时改用**订单实际的 outTradeNo**（而非本次请求新生成的号），保证 `pay_order.out_trade_no` 与 `group_buy_order.out_trade_no` 一致，回调结算才能反查到拼团订单。

## 五、前端对接说明

### 5.1 接口信息

- **URL**：`POST /api/v1/groupbuy/lockGroupBuyOrder`
- **登录态**：JWT，由 `AuthInterceptor` 解析注入 openid（请求体中的 userId 不作为身份依据）
- **Content-Type**：`application/json`

### 5.2 请求参数

```jsonc
{
  "activityId": 10001,        // 必填，拼团活动ID
  "productId": 1,             // 必填，商品ID（Long）
  "teamId": null,             // 开团传 null；参团传目标团 teamId
  "outTradeNo": "10475935537411", // 幂等号，见下方规则；可先不传
  "source": "source01",       // 可选
  "channel": "channel01"      // 可选
}
```

**outTradeNo 传递规则（推荐实现）**：

1. 用户进入收银台/点击"发起拼团"时，前端本地生成一次幂等号并保存在页面状态中（建议 14 位纯数字，与服务端格式一致，如时间戳+随机数）
2. 之后该笔单据的**所有重复提交都携带同一个值**
3. 只有开始一笔全新订单（上一单已支付/已取消/用户主动放弃）时才重新生成
4. 完全不传也可以——后端业务防重会复用待付款订单，只是跨活动场景下严格性稍弱

### 5.3 响应示例

```jsonc
{
  "code": 200,
  "info": "成功",
  "data": {
    "teamId": "01849553",           // 团ID，参团/展示用
    "outTradeNo": "10475935537411", // ★务必保存，重试时回传；也是后续查单凭证
    "payUrl": "<form>...(支付宝支付表单HTML)</form>"
  }
}
```

> `payUrl` 是支付宝 pagePay 返回的表单 HTML，需写入页面触发提交跳转支付。

### 5.4 状态码处理

| code | 含义 | 前端处理建议 |
|------|------|--------------|
| 200 | 成功 | 保存 data，渲染支付表单 |
| 401 | 未登录 | 跳登录页 |
| 10201 (E0201) | 请先完善账号信息（未绑定手机号） | 引导去完善资料 |
| 10103 (E0103) | 参与此拼团次数已达上限 | toast 提示，禁止继续重试 |
| 500 | 未知失败 | 提示稍后重试 |

### 5.5 防重复点击交互建议

```
点击[发起拼团] → 按钮置 loading（防抖）
  ├─ 成功 → 缓存 {teamId, outTradeNo} → 展示支付表单
  │         用户中断支付后再次点击 → 带 outTradeNo 重试 → 服务端返回同一订单
  └─ 失败 → 按钮恢复，提示错误
```

配合后端两层防护后的效果：

| 场景 | 修复前 | 修复后 |
|------|--------|--------|
| 同一单快速重复点击 | 各生成新订单+新团队 | 返回同一笔订单（同 teamId/outTradeNo） |
| 不传幂等号的旧客户端重复点击 | 产生脏数据 | 复用待付款订单，不新建 |
| 订单超时未支付（15 分钟） | — | 超时退单任务释放，可重新下单 |

## 六、边界与注意事项

1. **业务防重的粒度是"用户 × 活动"**：同一活动下存在待付款订单时，即使这次想参另一个团，也会返回已有订单。这是有意为之（避免刷单/脏数据）；若产品上需要"换团"，需先对原订单走退单流程释放。
2. **限购计数（UserTakeLimitRuleFilter）统计的是全部状态的订单**，与幂等无关：退款后的订单也计入 takeLimitCount。防重命中时不会执行规则链，因此不会额外消耗限购额度。
3. **数据库唯一键兜底**：`uk_out_trade_no` 保证极端并发下同一幂等号只会落一条记录；并发同时通过防重检查的场景理论上仍可能各开一团（第 2 层为查询-后插入模式），如有更高要求可升级为分布式锁或唯一索引 `(user_id, activity_id, status)` 的方案。
4. **回调链路依赖 out_trade_no 一致性**：`pay_order` 与 `group_buy_order` 必须共用同一个 outTradeNo（本次已在 Controller 强制对齐），前端不要自行改动响应中返回的值。
