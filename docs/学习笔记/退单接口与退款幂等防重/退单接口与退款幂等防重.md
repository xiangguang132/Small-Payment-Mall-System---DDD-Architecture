# 退单接口接入与退款幂等防重 — 设计笔记

> 主题：`IOrderService.refundOrder` 从「零调用的死方法」到「对外接口 + 越权防护 + 退款幂等防重」的演进过程
> 分支：`group-buy-dev` ｜ 涉及模块：api / domain / infrastructure / app(trigger)

---

## 一、背景：`refundOrder` 原本是零调用的死方法

起初 `IOrderService` 里只有声明、`OrderService` 里有实现：

```java
// IOrderService.java
boolean refundOrder(String outTradeNo);
```

全项目里没有任何地方调它——既没有 controller，也没有 listner / job。需要为它找一个合理的接入点。

### 关键澄清：为什么不需要单独传 userId

最初担心 controller 要传 userId，但确认后发现：

- `refundOrder(String outTradeNo)` 内部会走 `orderRepository.queryPayOrderByOutTradeNo(outTradeNo)`，
  拉出**完整订单实体**（`PayOrderEntity` 含 `userId` / `openid` 字段，见 `PayOrderEntity.java:19`）。
- 所以 **userId 已经在订单实体里**，HTTP 层只需要传 `outTradeNo`。
- **但** `queryPayOrderByOutTradeNo` 只按 `outTradeNo` 查、不区分用户（`OrderRepository.java:91`），
  因此「归属校验」必须靠 service 层用 `userId` 显式判断来完成。

---

## 二、决策：接入点放在 `MarketTradeController`，面向 C 端自助退款

通过确认，退款接口的调用方是 **C 端用户自助退款**（「我的订单 → 申请退款」），因此：

1. **放在 `MarketTradeController`**（`/api/v1/trade/`），与 `lock_pay_order` 同属交易动作，语义自洽。
2. **归属校验必须做，且放在领域层（service）**，而不是 controller：
   - 否则任何人拿别人的 `outTradeNo` 就能退款，是越权漏洞。
   - 校验与 `alipayPort.tryLock` 防重锁需在同一方法边界（同一线程/事务），放 service 最正确。

### 已落地的改动（第一批）

| 文件 | 改动 |
|---|---|
| `IOrderService.java` | 签名改为 `boolean refundOrder(String userId, String outTradeNo)` |
| `OrderService.java` | 实现加 `userId` 参数；查单后先做归属校验，失败抛 `AppException(FORBIDDEN, "无权退该订单")` |
| `MarketTradeController.java` | 新增 `POST /api/v1/trade/refund_order`，从 `request.getAttribute("openid")` 取当前用户（兜底 `request.getUserId()`），调 `orderService.refundOrder(userId, outTradeNo)` |
| `RefundOrderRequest.java`（新增） | 请求 DTO：`userId`、`outTradeNo` |

### 威胁模型

- `AppException(FORBIDDEN)` → `GlobalExceptionHandler` 映射 HTTP **403**，`code/info` 原样返回。
- `AppException(NOT_FOUND)` → HTTP **404**。
- 因此 `refund_order` 的 catch 里**必须把 `AppException` 重新抛出**交给全局处理器，
  而不是像 `lock_pay_order` 那样统一 catch-all 吞成 `UN_ERROR(500)`，否则会丢失 403/404 语义。

```java
} catch (AppException e) {
    // 归属校验失败(403)、订单不存在(404)等业务异常交由全局异常处理器
    throw e;
} catch (Exception e) {
    // 非业务异常
    return ... UN_ERROR ...;
}
```

## 三、防重现状分析：有一个「不完整」的防重

初始 `refundOrder` 的防重情况：

- **已支付退单 `doRefundPaidOrder`**：有 Redisson 分布式锁
  ```java
  if (!alipayPort.tryLock(outTradeNo)) {
      throw new AppException(UN_ERROR, "订单处理中，请勿重复操作");
  }
  ```
  - key 是 `outTradeNo`，同一单号并发退单只有一个能执行。
- **未支付退单 `doCloseUnpaidOrder`**：无锁（`changeOrderPayClose(outTradeNo)` 直接改状态）。
- **缺少「退款幂等」**：分布式锁只防**同一时刻的并发**，防不住**顺序重复请求**
  （第一次已退款成功，用户再点一次——虽然最终会被 `UNPROCESSABLE_ENTITY` 兜住，
   但在「退款请求已发起、支付宝未回调、状态未落库」的窗口里，两次请求可能同时打到支付宝）。

### 结论：优先补「数据库层的退款幂等」

- 分布式锁是「尽力而为」，数据库乐观锁式状态演进才是「强约束」。
- 锁只保并发；真正要防的是**同一订单永不重复进支付宝退款**。
- 未支付退单（幂等关单）资金风险小，可暂缓。

---

## 四、方案定稿：REFUNDING 中间态 + 数据库乐观锁式状态演进

### 思路

调支付宝退款前，先把订单从 `PAY_SUCCESS` / `DEAL_DONE` **原子地**改成 `REFUNDING`（退款中）。
那条带 `status IN (...)` 的 `UPDATE` 只允许一个请求影响 1 行；后续并发/重复请求影响 0 行，
直接判为「已受理」，不再进支付宝。退款结束后结果再回写 `REFUND`（成功）或回滚原状态（失败可重试）。

### 状态机

```
PAY_SUCCESS ─┐                     成功 → REFUND
             ├→ REFUNDING ─────────┤
DEAL_DONE  ──┘                     失败 → 回滚原支付状态（可重试）
```

### 为什么不能用旧 `changeOrderRefundSuccess` 直接收尾

旧 SQL：`... set status='REFUND' where out_trade_no=#{..} and status='PAY_SUCCESS'`

- 它直接把 `PAY_SUCCESS → REFUND`，无中间态，且 `and status='PAY_SUCCESS'` 是硬编码。
- 一旦引入 `REFUNDING`，回写时 status 已是 `REFUNDING`，`and status='PAY_SUCCESS'` 就 match 不上。
- 所以必须用**带 `fromStatus` / `toStatus` 参数**的通用回写方法替代之，并**删除原方法**，避免双份。

```java
/** 乐观锁占位：把 PAY_SUCCESS/DEAL_DONE 置为 REFUNDING。命中 0 行说明已有人在退或已退。 */
boolean changeOrderRefunding(@Param("outTradeNo") String outTradeNo);

                                @Param("fromStatus") String fromStatus,
                                @Param("toStatus") String toStatus);
```

### ③ `pay_order_mapper.xml` — 两条 SQL

```xml
<!-- 删 changeOrderRefundSuccess -->
<update id="changeOrderRefunding" parameterType="java.lang.String">
    update pay_order set status = 'REFUNDING', update_time = now()
    where out_trade_no = #{outTradeNo}
      and status in ('PAY_SUCCESS', 'DEAL_DONE')
</update>

<update id="changeOrderRefundResult" parameterType="java.lang.String">
    update pay_order set status = #{toStatus}, update_time = now()
    where out_trade_no = #{outTradeNo}
      and status = #{fromStatus}
</update>
```

### ⑥ `OrderService.java` — 改造 `doRefundPaidOrder`

```java
// 已支付退单
private boolean doRefundPaidOrder(String outTradeNo, PayOrderEntity payOrderEntity) {
    // 数据库乐观锁占位：只允许一个请求把 PAY_SUCCESS/DEAL_DONE -> REFUNDING
    if (!orderRepository.changeOrderRefunding(outTradeNo)) {
        throw new AppException(ResponseCode.CONFLICT, "该订单退款已受理，请勿重复操作");
    }
    // 记录原支付状态，退款失败时回滚
    String fromStatus = payOrderEntity.getOrderStatus().getCode();
    try {
        boolean isRefundSuccess = alipayRefundPort.refund(outTradeNo, null, payOrderEntity.getTotalAmount());
        if (!isRefundSuccess) {
            // 失败：回滚 REFUNDING -> 原状态，允许用户重试
            orderRepository.changeOrderRefundResult(outTradeNo, OrderStatusVO.REFUNDING.getCode(), fromStatus);
            throw new AppException(ResponseCode.UN_ERROR, "支付宝退款失败");
        }
        // 成功：REFUNDING -> REFUND
        orderRepository.changeOrderRefundResult(outTradeNo, OrderStatusVO.REFUNDING.getCode(), OrderStatusVO.REFUND.getCode());
        return true;
    } finally {
        // 分布式锁可保留（与支付宝回调等其它链路做单号互斥），也可去掉（数据库乐观锁已兜底）
        alipayPort.unlock(outTradeNo);
    }
}
```

## 六、新旧方案行为对比

| 场景 | 旧方案（REFUND 一步到位） | 新方案（REFUNDING 居间） |
|---|---|---|
| 重复/并发退 | `status='PAY_SUCCESS'` 已改走，抛「状态不可退单」 | `changeOrderRefunding` 返回 0 行，抛 `CONFLICT`「已受理」 |
| 退款失败 | 卡死无法重试 | 回滚 `REFUNDING`→原状态，可重试 |
| 退款成功 | `REFUND` | `REFUNDING`→`REFUND` |
| 流程完整性 | 无中间态提示 | 有 `REFUNDING`「退款中」状态 |
