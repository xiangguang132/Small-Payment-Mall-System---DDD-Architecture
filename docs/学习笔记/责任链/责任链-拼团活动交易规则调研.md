# 责任链调研：group-buy-market `link` 与 CC 拼团活动交易规则复写评估

## 调研范围

- 参考项目：`D:\code\group-buy-market`
- 目标源码：
  - `group-buy-market-types\src\main\java\cn\bugstack\types\design\framework\link`
  - `group-buy-market-types\src\main\java\cn\bugstack\types\design\framework\tree`
- 本地工程：`D:\code\s-pay-mall-ddd-cc`
  - 本地目前已有 `s-pay-mall-ddd-types\...\design\framework\tree`
  - 本地目前没有 `design\framework\link`

本文只做调研，不修改业务代码。

## 结论摘要

1. `link` 是责任链模式的通用脚手架，不是严格意义上的模板方法模式。
2. `link` 目录下有两套模型：
   - `single_model`：节点自身持有 `next`，由每个节点显式调用 `next()` 继续流转。
   - `muti_model`：使用自定义 `LinkedList` 容器保存多个 `ILogicHandler`，由 `BusinessLinkedList` 遍历执行。
3. `tree` 不是链表，也不是物理上的树容器；它是“策略路由/逻辑决策树”。链路是顺序执行，树是按条件选分支。
4. 参考项目生产环境主要使用 `muti_model`，实现了“拼团锁单规则过滤”和“支付结算规则过滤”两条链。
5. 复写时，通用责任链框架可以按需搬运；业务规则、实体、Repository、调用入口必须按 CC 当前 DDD 分层本地化，不能整包照抄。

## 1. 是不是模板

如果“模板”指的是“可复用的抽象基类、通用脚手架”，那么 `link` 是模板。

如果“模板”指的是 GoF 的 Template Method 模式，`link` 并不严格是：

- `AbstractLogicLink` 只是提供 `next`、`appendNext()`、`next()` 这几个链式能力。
- 责任链没有固定算法骨架，每个节点自己写 `apply()` 业务逻辑，并决定是否调用 `next()`。
- 真正偏模板方法的是同目录 `tree` 下的 `AbstractStrategyRouter` / `AbstractMultiThreadStrategyRouter`：
  - `router()` 固定了“取下一节点 -> 执行 -> 没有则执行默认策略”的骨架。
  - `AbstractMultiThreadStrategyRouter.apply()` 固定了“先 `multiThread()`，再 `doApply()`”的骨架。

## 2. 怎么实现的

`link` 统一使用三个泛型：

```text
<T, D, R>
T = 请求参数
D = 节点间共享的动态上下文
R = 链式执行后的返回结果
```

### 2.1 `single_model`

核心类：

- `ILogicChainArmory<T, D, R>`：定义 `next()`、`appendNext()`。
- `ILogicLink<T, D, R>`：继承 `ILogicChainArmory`，增加 `apply()`。
- `AbstractLogicLink<T, D, R>`：持有 `private ILogicLink<T, D, R> next`。

实现方式：

```java
ruleLogic101.appendNext(ruleLogic102);
return ruleLogic101;
```

节点内部显式调用：

```java
public R apply(T request, D context) throws Exception {
    // 当前规则
    return next(request, context);
}
```

这里的“链”是对象引用组成的单向链：`next` 保存在每个节点对象里。当前节点要放行，就必须自己调用 `next()`；当前节点直接返回，则链路提前终止。

### 2.2 `muti_model`

核心类：

- `ILink<E>`：定义 `add/addFirst/addLast/remove/get/printLinkList`。
- `LinkedList<E>`：自定义双向链表，内部有 `Node<E>`，字段为 `prev/item/next`。
- `ILogicHandler<T, D, R>`：定义 `apply()`，默认 `next()` 返回 `null`。
- `BusinessLinkedList<T, D, R>`：继承 `LinkedList<ILogicHandler<T, D, R>>`，同时实现 `ILogicHandler<T, D, R>`。
- `LinkArmory<T, D, R>`：通过构造参数把多个 `ILogicHandler` 按顺序加入 `BusinessLinkedList`。

实现方式：

```java
LinkArmory<TradeRuleCommandEntity, DynamicContext, FeedBackEntity> armory =
        new LinkArmory<>("交易规则过滤链", activityRuleFilter, takeLimitRuleFilter);

BusinessLinkedList<TradeRuleCommandEntity, DynamicContext, FeedBackEntity> link =
        armory.getLogicLink();
```

`BusinessLinkedList.apply()` 的执行逻辑是：

```text
从 first 开始
  -> 调用当前 handler.apply()
  -> 如果返回值非 null，直接返回
  -> 如果返回 null，继续走 next
  -> 直到链表结束
```

因此 `muti_model` 的节点不持有“下一节点”，链的顺序由 `LinkedList` 的 `Node` 物理保存。规则想放行时调用 `next()`，而 `ILogicHandler` 默认的 `next()` 返回 `null`，于是外部循环继续走到下一个 handler。

## 3. 与同目录 `tree` 的区别

### 3.1 结构定位不同

`tree` 目录包含：

- `StrategyHandler<T, D, R>`
- `StrategyMapper<T, D, R>`
- `AbstractStrategyRouter<T, D, R>`
- `AbstractMultiThreadStrategyRouter<T, D, R>`

`tree` 不是物理树，也不是链表。`tree` 框架本身没有通用 `Node`、`left`、`right`、`parent` 等容器。每个具体节点通过 Spring 注入下一节点的 `StrategyHandler`，再通过 `get()` 决定下一节点：

```java
// RootNode
@Override
public StrategyHandler<...> get(...) {
    return switchNode;
}

// MarketNode 可以按条件选择不同分支
@Override
public StrategyHandler<...> get(...) {
    return activityOk ? tagNode : errorNode;
}
```

所以：

- 物理上，`tree` 只是对象引用组成的逻辑图，没有通用链表或树节点类。
- 逻辑上，`tree` 是多叉决策路由，每个节点只执行一条被选中的分支。
- `link` 物理上确实有链表结构：
  - `single_model`：每个 `AbstractLogicLink` 持有 `next` 引用。
  - `muti_model`：`LinkedList` 有 `Node.prev` 和 `Node.next`，执行时只沿 `next` 方向遍历。

### 3.2 对比表

| 维度 | `link` | `tree` |
| --- | --- | --- |
| 定位 | 责任链、规则过滤 | 策略路由、决策树 |
| 核心接口 | `ILogicLink` / `ILogicHandler` | `StrategyHandler` / `StrategyMapper` |
| 下一节点来源 | 已排好的 `next` 或链表顺序 | 当前节点 `get()` 动态返回 |
| 执行路径 | 顺序线性执行，非 null 短路 | 每次按条件选择一条分支 |
| 是否多叉 | 通常单链，不能自然分叉 | 天然支持多叉 |
| 物理结构 | 单链是对象引用；多链是自定义双向链表 | 无通用 Node/链表，对象引用组成的逻辑图 |
| 使用场景 | 活动状态、用户次数、单号、有效时间等顺序过滤 | 试算 Root/Switch/Market/Tag/End 等分支决策 |

### 3.3 是链表还是其他

- `single_model` 是对象引用形成的单向链。
- `muti_model` 是自定义双向链表容器，执行时按单向 `next` 顺序遍历。
- `tree` 不是链表，也不是传统二叉树；它是策略路由树，结构逻辑上由节点自行决定。

## 4. 多链路与单链路的区别

参考项目目录写的是 `muti_model`，推测原意是 `multi_model`。这里对比的是 `single_model` 与 `muti_model` 两种责任链实现。

| 维度 | `single_model` | `muti_model` |
| --- | --- | --- |
| 下一个节点 | 保存在 `AbstractLogicLink.next` | 保存在 `LinkedList.Node.next`，handler 不持有 next |
| 流转方式 | 节点内显式调用 `next()` | `BusinessLinkedList.apply()` 循环遍历 |
| 装配方式 | 调用 `appendNext()` 串联 | `LinkArmory` 把 handlers 加入链 |
| 多链复用 | 同一个 Spring Bean 被多个链 `appendNext` 会互相覆盖 `next`，有状态污染风险 | 每次创建独立 `BusinessLinkedList`，同一 handler 可以被不同链复用 |
| 适用场景 | 简单、固定、单实例链 | 规则过滤、多套链、Spring Bean 装配 |
| 参考项目生产使用 | 未用于生产，只有 `Link01Test` 示例 | 用于锁单和结算规则过滤 |

结论：如果 CC 要做“拼团活动交易规则过滤”，建议使用 `muti_model`。它把链顺序从业务节点中拆出来，更适合 Spring 单例 Bean、工厂装配和后续动态调整顺序。

## 5. 参考项目用该链路实现了什么功能

### 5.1 拼团锁单规则过滤

调用入口：

- `TradeLockOrderService.lockMarketPayOrder()`
- 工厂：`TradeRuleFilterFactory`
- 链对象：`tradeRuleFilter`

链顺序：

```text
ActivityUsabilityRuleFilter
  -> UserTakeLimitRuleFilter
```

功能：

- `ActivityUsabilityRuleFilter`
  - 根据 `activityId` 查询活动。
  - 校验活动状态是否为生效状态，不合法抛 `E0101`。
  - 校验当前时间是否在活动开始/结束时间内，不合法抛 `E0102`。
  - 把 `GroupBuyActivityEntity` 写入 `DynamicContext`。
- `UserTakeLimitRuleFilter`
  - 从上下文读取活动 `takeLimitCount`。
  - 统计用户在该活动下已参与的订单数。
  - 超过限制抛 `E0103`。
  - 返回 `userTakeOrderCount`，供锁单时构建数据库唯一索引使用。

### 5.2 支付结算规则过滤

调用入口：

- `TradeSettlementOrderService.settlementMarketPayOrder()`
- 工厂：`TradeSettlementRuleFilterFactory`
- 链对象：`tradeSettlementRuleFilter`

链顺序：

```text
SCRuleFilter
  -> OutTradeNoRuleFilter
  -> SettableRuleFilter
  -> EndRuleFilter
```

功能：

- `SCRuleFilter`
  - SC 渠道黑名单规则，参考项目中暂时是放行占位。
- `OutTradeNoRuleFilter`
  - 根据 `userId + outTradeNo` 查询营销支付订单。
  - 查询不到时抛 `E0104`，表示外部单号不存在或已退单。
  - 把 `MarketPayOrderEntity` 写入上下文。
- `SettableRuleFilter`
  - 查询拼团团队。
  - 校验用户支付时间早于拼团有效结束时间，否则抛 `E0106`。
  - 把 `GroupBuyTeamEntity` 写入上下文。
- `EndRuleFilter`
  - 从上下文读取团队信息。
  - 组装 `teamId/activityId/targetCount/completeCount/lockCount/status/validStartTime/validEndTime/notifyUrl` 返回。

### 5.3 示例测试

- `Link01Test`：验证 `single_model`。
- `Link02Test`：验证 `muti_model`，同时暴露 `demo01`、`demo02` 两条链。

## 6. 复写建议：直接誊抄还是本地化修改

结论：

```text
通用责任链框架：可以按需搬运，但不能盲目整包复制。
业务规则、实体、Repository、调用入口：必须本地化修改。
```

原因：

1. CC 当前只有 `tree`，没有 `link`。如果把 `link` 通用类复制到 `s-pay-mall-ddd-types\...\design\framework\link`，泛型结构和包名可以保持一致。
2. CC 的拼团领域模型和参考项目不同：
   - 参考项目使用 `TradeRuleCommandEntity`、`TradeRuleFilterFeedBackEntity`。
   - CC 当前使用 `GroupBuyActivityEntity`、`GroupBuyOrderAggregate`、`IGroupBuyRepository` 等。
   - 字段类型也有差异，例如 CC 使用 `LocalDateTime`、`Long activityId`。
3. CC 是统一订单/支付入口，不能照搬参考项目的 `TradeLockOrderService`、`TradeSettlementOrderService` 形成第二套支付链路。
4. 当前 CC 的锁单规则已经以 `if` 形式写在 `GroupBuyOrderService` 里，应该把这些规则抽取成责任链节点，而不是再叠一套重复逻辑。
5. 参考项目生产使用的是 `muti_model`，本地也建议使用它。

推荐落地方式：

```text
1. 拷贝通用链路框架
   s-pay-mall-ddd-types/.../design/framework/link

2. 创建 CC 拼团规则模型
   GroupBuyRuleCommandEntity
   GroupBuyRuleDynamicContext
   GroupBuyRuleFilterBackEntity

   注意：这里不是要新增或替换 `GroupBuyOrderEntity`、`GroupBuyTeamEntity`。
   现有订单、团队、活动模型继续保留；这 3 个文件是规则链专用 DTO：

   - 入参：规则链需要的外部参数，例如 `userId/activityId/outTradeNo`。
   - 上下文：多个规则节点之间共享的数据，例如查询出的活动、团队、订单。
   - 出参：最后一个规则节点返回给调用方的结果。

   如果沿用 CC 现有写法，也可以把上下文做成规则链工厂的内部
   `DynamicContext`，类似 `DefaultActivityStrategyFactory.DynamicContext`，
   这样规则模型就只需要 2 个独立文件。

3. 创建规则节点
   ActivityUsabilityRuleFilter
   UserTakeLimitRuleFilter
   ChannelBlacklistRuleFilter（如需要）
   OutTradeNoRuleFilter（如需要）
   SettableRuleFilter（如需要）
   EndRuleFilter

4. 创建规则链工厂
   使用 LinkArmory 装配 BusinessLinkedList

5. 接入现有入口
   GroupBuyOrderService.lockGroupBuyOrder
   AliPayController / OrderPaySuccessListener 的拼团结算分支

6. 补测试
   每个规则节点单测
   整条链短路测试
   规则通过后返回反馈结果测试
```

需要特别注意的是：

- `BusinessLinkedList` 是容器结构，链顺序在装配时确定。
- 不要在运行时频繁修改同一个链，避免并发问题。
- `DynamicContext` 应该是每次请求新建，不要复用同一个上下文。
- 规则节点要写业务规则和上下文，不直接操作基础设施 DAO，保持 CC 的 Repository 边界。
